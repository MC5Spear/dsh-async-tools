## 1. 总体架构与组合范围

### 1.1 单包两角色

宿主把插件配置组织成「行」，每行负责一次装配。本包使用同一个入口，再根据行配置是否有 `toolName` 选择角色：

- 无 `toolName`：宿主配置角色，提供生效配置快照、浏览器入口和提问接管服务，不注册工具。
- 有 `toolName`：工具角色，每行注册指定工具；命令、等待和派生工具在预设顶层，编排行在 delegation 组内取得隔离的 `workflowEngine`。

`toolName` 可选且无默认值，不标 volatile。缺字段不能等于自动装上命令执行器。宿主行由本包的 [bundle 声明](<../cordis.patch.yml>)提供；[包清单](<../package.json>)声明宿主行和两份预设补丁，以及浏览器入口。

bundle patch 是宿主支持的组合树覆盖配置。它把本包声明加入宿主组合，不修改宿主源码或随宿主发布的文件。预设由宿主注册表管理，插件不另建用户预设目录。

### 1.3 服务声明与作用域

入口静态声明九项必需服务：`tools`、`jobs`、`shell`、`shellEnv`、`subagents`、`timer`、`sessionProjections`、`agents`、`workingDirectory`。宿主行和工具行都采用该声明。任一服务缺席时，插件等待服务而不启动，不能绕过依赖注入直接读取上下文。

其中，`sessionProjections` 只读原生子代理模型策略的会话投影，用于 3.6 的目标适用性判断；`agents` 查询子代理当前运行状态；`workingDirectory` 在命令启动前提供有效目录。

新增依赖是否在宿主行和预设行可见，必须通过真实 cordis 装配验证。替身对象上有同名字段，只能证明替身准备了该字段。

`agents` 是公开 Agent 注册表（服务键 `agents`，dsh-agent 的 `AgentRegistry`）：`get(id)` 返回当前驻留的 Agent 或 `undefined`；Agent 的公开 `status` getter 只取 `running` 或 `idle`，`idle` 含维护阶段；状态转换发布 `agent/status` 事件，载荷 `{agent, status}`。目录条目只证明会话存在过，注册表驻留才证明当前有驱动；两者分开消费。`startActivation` 接受的 parent 必须是注册表中同一活 Agent 对象。工具只在先确认合法子代理关系后查询目标注册表，不读子代理私有日志；查询失败不伪造非运行状态。

可选审批、`llm` 运行时、模型选择设置（`subagentModelSelection`）、会话查询、系统提示及引擎按调用或运行时注入取得：`llm` 承担派生路由预检（`resolveCallConfig`）与路由查询的目录读取（`listProviders`／`listModels`／`resolveModelInfo`），`subagentModelSelection` 承担派生策略与查询适用性的实时读取；两者缺席按 3.3／3.6 的可读失败处理，不能把可选服务缺席升级成全部工具永久不可用。`workflowEngine` 仍只在 delegation 隔离组内取得，其依赖和失败处理见 3.4。固定依赖与可选读取要分别测试。

工具行上下文覆盖组合内多个 Agent，不等于某个父子会话关系。消息监听必须按 `payload.agent.id === exec.agent.id` 过滤接收主体；状态信号按等待目标 id 匹配，作业事件按确切 owner 和目标 job id 匹配。

## 2. 共用预算、唤醒与结果机制

### 2.1 单一总截止

`async_wait` 在 execute 入口建立单调时钟起点和夹紧后的总截止。入口取消可以零查询返回；有效等待参数缺失仍按需求报错。`wait_ms` 为 0 时按零等待执行：不夹紧到 `minWaitMs`、不武装等待、不重试、不轮询，只做一次入口检查（已到消息扫描、目标确认与状态快照、就绪内容汇集）后立即交回。

```text
入口取消检查 → 解析参数 → 订阅消息与目标事件 → 武装总截止
             → 扫描已到未领消息、确认合法目标及当前状态
             → 在剩余预算内查询／重试／等待／轮询
             → 已有终态证据优先，否则按唤醒、取消或到期交回
             → 撤监听、计时和落败等待
```

- 总截止的定时器在参数解析后立即武装一次（arm，挂载启动），起点即单调时钟 t0。消息与目标事件订阅在武装之前挂好：先订阅、再扫描，避免唤醒空窗，与 2.2 同一口径。存在性屏障（即需求 2.1.1 的存在性检查，含其重试——同一机制，本文简称屏障）、先到扫描、终态判定和等待段全部发生在武装之后，计入总预算。屏障或入口检查之后不得以全额预算重新武装；中途任何阶段都不重置 t0。
- 等待初始化逐项登记已建立的订阅、定时器与等待登记；任一步失败时先撤销前序已建立资源，按本次调用的可控错误返回，不留遗留监听，也不成为进程级未处理拒绝。已创建的信号 Promise 在提前返回（入口检查即返回、终态即返回、存在屏障切断）之后仍可能拒绝，创建点或出口承接其拒绝，不遗留无人承接的派生 Promise。
- 查询、重试睡眠和等待只取得 `deadline - now` 的剩余值；不能重新夹紧到 `minWaitMs` 把总预算扩大。屏障重试的每次睡眠取 `min(pollIntervalMs, deadline - now)`，剩余不正时按到期返回，不把屏障段排除在预算外。
- 剩余值不正时直接到期，不把零传给使用零表示「不装定时器」的宿主帮助函数，也不调用要求正超时的 `jobs.wait`。
- **竞速规则**：辅助查询——入口关系定性（3.2）、存在屏障重试、查无出口的已知清单、收敛后复查——无论在哪个阶段发起，都与工具取消、可处理消息、总截止同时竞速，不只与到期竞速。任一先到即切断该次查询等待，并按先到信号的口径交回；宿主查询忽略取消信号或挂起时，消息与取消仍及时交回（真机响应窗口按 8.1）。`subagents.listChildren(parentId, signal)` 支持取消，调用取消和截止信号传入本包发起的每一次该类查询。已知清单是可选诊断：不挡已证主结果，也不挡控制信号。这四类查询的竞速对象都是活信号——等待中新到的消息各自解析其唤醒 Promise，先到即切断，查询挂起不以窗口外的时长拖住它们。零等待调用不进入竞速：异步检查只发起一次，竞速对象仅为工具取消；结果未回即按未证实交回。
- **唯一例外**：入口关系定性携带的先到消息已被入口分支消费，不再是竞速成员，定性窗口就是这条消息的唯一出口；窗口自身受固定响应上限约束，不随 `pollIntervalMs` 放大（3.2）。
- **退出纪律**：在途查询逐次串行——轮询链内上一拍结束后按剩余预算再排下一拍，不用异步 interval 叠加查询；目录列举与注册表状态读取同此纪律。收敛后复查发起前先撤销轮询续排（在途拍结束后不再续），复查不与轮询在途拍叠加成两路并发；主循环内（复查、状态读取）任意时刻在途目录查询至多一路。任何目录查询发起前检查剩余预算，剩余不正不再发起；调用退出后不再续排、不再新发。
- 到期后不无界 await 复查或错误清单查询。查询异常与超时保持未证实状态，不变成查无或目标完成。
- 落败 Promise（竞速中未胜出一方）的后续拒绝必须接住，取消尽力转发。若直接取得 session observation，迟到成功也释放租约；不得丢掉资源。取消底层 I/O 不保证物理操作瞬间停止，但不能阻止本工具交回控制。
- JS 同步段和宿主前置审批不受此定时器抢占，不宣传硬实时。必要渲染采用受控长度，不引入无界后置工作。
- 命令与编排的首次等待同口径：`yield_ms` 从等待段开始即武装，撤销后的完成优先复查在剩余时间外不再取得新预算；交回控制的原因按消息、取消、预算到期与终态分别说明，取消不并入预算到期；工具描述宣称的总时长与该口径一致。
- 时间判据：全程上界按有效 `wait_ms`（请求值经需求 5.2 上下限夹紧后的值）计量——请求低于 `minWaitMs` 被抬到下限时，断言与上界都用夹紧后的值（请求 60 ms、下限 250 ms 时上界 550 ms），不按请求值断言；请求 0 是唯一例外，不夹紧、按零等待口径计量。以任意有效 `wait_ms` 调用，`async_wait` 的全程上界均为 `有效 wait_ms + 300 ms` 固定调度容差，包括需要屏障重试的情形，不追加轮询间隔或重试时长。屏障重试至多三拍；每拍查询和睡眠只取总截止前的剩余预算，剩余不正即返回，不要求用完三拍。总截止不变以真时钟平上界断言（按真实时钟计量全程时长、断言不超过固定上界）与变异测试锚定（对轮询间隔、重试次数等参数做受控修改后断言仍成立）锁定：改变轮询间隔或实际重试次数不得延长总预算。300 ms 是现有等待计时单元装置的固定调度容差，不是可分配给查询、重试或等待的新预算。目录查询挂起专项采用更严格的 `有效 wait_ms + 200 ms` 上界，对应现有装置的 250 ms 预算、450 ms 上界。上述数值是测试判据，不表示目标宿主已通过验证；真机按 8.1 分层单独标定固定调度容差，不按轮询间隔或重试次数追加时长。

待核验对象：dsh `0.2.1-rc.4` 的 `@deepseek-ai/dsh-subagent` 中 `listChildren(parentId, signal)` 与 `@deepseek-ai/dsh-jobs-local` 中 `wait` 的取消实现，以及本包统一等待与两个目标适配模块。这里不指定未经重核的行号；目标宿主行为尚需回归。

### 2.2 消息集合和入口扫描

消息部件提供单次调用拥有的 `{promise, dispose}`，先订阅、再扫描主体待领取列表，避免订阅空窗。判断规则为：

1. 收件人是本次调用主体。
2. 消息此刻在该主体的 `nextStep` 中。
3. 来源命中其一：`source.kind === 'user'`（用户插话）；`source.form === 'notice'`（一次性通知，含其他子代理的结算通知）；`source.form === 'relay'`（代理转达，如 `agent-message`）。`form` 为 `instructions`、`catalog`、`snapshot`、`recall` 或无 `form` 的上下文消息不命中；进度事件、目录与配置快照不因角色为 user 就命中。

本包迟到作答通知（`source.kind === 'async-tools-late-answer'`）走专门唤醒分支，返回携带题目摘要；通用判定对它不重复命中，同一消息不产生两个竞争说明。专门分支对本主体视同高优先通知：无目标与有目标 `async_wait` 都被它唤醒（有目标时按 message 出口交回并附其余目标已证状态）；按 `senderSessionId` 的目标过滤（2.2 末段、需求 9.3.3）适用于外来消息，不适用于本包自产的作答通知——题目是本主体投的，作答到达即本主体可处理的变化。

`agent/inbox/inserted` 不带落点，按 message id 回查 `nextStep`。事件提交后发生，正常等待期间不会自行领取；入口扫描按同一判定扫 `nextStep` 全列表，处理先到消息。列表读取失败保守为未证实，不使信号 Promise 无处理拒绝。

`nextTurn` 的 `queue` 不进入唤醒判断，不擅自移到 `nextStep`；goal 轮次驱动经 `followup` 投递，落 `nextTurn`，同样不唤醒。普通工具结果直接进入会话结果，不自动灌回自己的收件箱；额外上下文可能进入 `nextStep`，因此不能盲扫所有 user-role 项。

这套判定统一用于三个等待入口：`async_wait` 与 `async_run`／`async_workflow` 的首次等待。三个入口共用同一消息部件与同一先到扫描；无目标等待在等待开始前已到达的可处理消息立即交回，有目标等待与首次等待只按目标条件与用户插话交回（3.2），先到的非目标通知留在收件箱按宿主节奏领取，不因先到而提前结束等待。

通知只作为交回控制理由。目标结算单独按 sender／job id 或公开状态证据判断，不以其他子代理、其他命令的消息改变目标状态。有目标等待与首次等待对 `notice`／`relay` 类消息按来源过滤：仅当消息的 `senderSessionId` 命中目标列表中的子代理时，该消息才构成目标变化并结束等待（3.2）；目标作业的完成不经消息通道，由作业事件通道判定。无目标等待被任一可处理消息唤醒。消息唤醒胜出后复查目标当前状态（作业查快照、子代理查注册表现读），已停止运行按目标结果返回，不因消息先到诱导重复等待——该复查对 user 插话、notice、relay 与目标自身的结算通知一律适用；停止结果与并存消息说明并呈（3.2）。返回包含目标句柄和唤醒原因，不替宿主消费通知正文。唤醒原因中的摘要取消息自带的 `summary`：`relay`／`notice` 类消息可能不带，空档时给回退文案并优先点名来源（宿主契约：`agent-message` 与 `subagent-settled` 两个 `kind` 恒带 `senderSessionId`，其余 `notice` 来源不保证）；契约被破坏、`senderSessionId` 缺席的形态按无名占位回退，不留空置的摘要括号（需求 2.1.3）。`user` 插话不作回退，其摘要不进渲染模板。

待核验对象：dsh `0.2.1-rc.4` 的 `@deepseek-ai/dsh-agent-loop` 中 inbox 插入与领取、`@deepseek-ai/dsh-llm` 的 `ContextForm`、`@deepseek-ai/dsh-subagent` 的 `createSettlementMessage` 与代理转达消息构造，以及 `@deepseek-ai/dsh-goal-round-driver` 的轮次投递。上述消息规则是目标约定；逐项静态核对与真实投递验证尚未完成，不沿用其他版本的行号作为证据。

### 2.3 取消、终态优先与通知

- 等待 signal 与后台工作的私有取消信号分开。取消本工具只撤销 waiter、监听和计时，不调用命令或编排 cancel。
- 竞速收敛及时撤销落败的 `jobs.wait`，防止遗留活 waiter 错误抑制作业通知。已有目标终态证据优先交付结果；到期后不等待无界补查来争取终态。消息唤醒胜出后复查发现作业已终态时，按终态结果返回并附并存的消息说明；退出信息、溢出文件找回线索等结局细节完整保留，并存说明附加表达，不替换终态详情。
- 本包作业转入后台时，交付账本为该作业挂一条保活等待链（下称保活链）：`jobs.wait` 按拍续排，作业结算前始终有本包 waiter 在册。拍长固定 60 秒，采用交叠续排，规则如下：
  - **预注册时机与频率**：每拍在其窗口过半时预注册下一拍，相邻两拍交叠半拍。按此机制，新注册间隔为半拍，每个后台作业每 30 秒至多一次新注册——该界指保活链注册的稳态；链入口过渡（零拍→链首拍）的新注册间隔为零拍半窗（首次等待预算之半，默认 10 秒），可短于 30 秒。调用频率不随作业数或批次数放大。
  - **空档消除与撤销**：当前拍到期结束时下一拍已注册，消除上一拍结束与下一拍注册之间的在册空档；两拍之一先行终态或被撤销时，另一拍经其 signal 撤销。
  - **链入口交接**：首次等待自身的 waiter 是链的零拍，链首拍在零拍窗口过半时预注册。零拍到期让出时首拍已在册；零拍因插话或取消提前结束而作业仍在运行时，退出处理内先撤零拍、同步注册首拍（若首拍尚未在中点预注册）；零拍内作业结算则撤销预注册，不挂链。「作业结算前任一时刻在册 waiter 至少一个」自首次等待武装起成立。
  - **抑制语义**：宿主以结算时刻仍有在册 waiter（`awaited`）抑制自带的完成通知；本包随后发出自带结果正文的完成消息（2.6），模型无需领取调用。
- 保活链在插件行卸载时整体撤销。撤销与终态释放产生的 resolve／reject（宿主 signal 中止走 reject）由链的注册点就地承接，不遗留未处理拒绝。撤销后或抑制条件未命中时宿主通知照发，按宿主消息原样计，不算本包重复投递，本包完成消息仍照常发出。宿主通知文本由宿主生成、固定含指向原生读取工具的引导句，该原文按宿主文本对待：「提示无失效指路」的核对范围只及本包文案（需求 9.3.5），抑制失败残留的宿主原文与 7.2 的卸载残留一同列入清点，清点判据登记于 8.2 预设隔离行。
- 外来作业（非本包工具注册、挂载本包等待行的主体经宿主公开作业服务可见的作业；适用口径见 2.6）不挂保活链：宿主对非本包作业的完成通知是常规交付，本包不代为抑制，只补未消费正文（2.6）。
- 宿主结算事件的 `awaited` 表示释放过活 waiter，不是模型已经领取工具结果的确认。本包不得把它宣传为用户已收到答案。
- 宿主完成通知的发出（含抑制未命中时的照发）还受 owner 存在、显式模型 kill、teardown 等条件影响。不另建重复通知系统，也不把宿主一般投递故障扩成产品补偿任务。
- 普通 `relay`、结算 `notice`、状态 `idle` 和最终文本分开。可续子代理自动结算 `notice` 本身可含收尾文本；显式 `send_message` 是另一条 `relay`，不能保证每次都有两条或固定先后。

待核验对象：dsh `0.2.1-rc.4` 的 `@deepseek-ai/dsh-tool-jobs` 作业通知与 `@deepseek-ai/dsh-subagent` 的 `notifySettlement`。须分别验证正常投递、父主体离开、显式停止与服务清理条件；不以接口在场或静态阅读代替投递验证。保活链的抑制效果（结算时在册 waiter 数量决定 `awaited`）与续排竞态窗口按同批核对。

### 2.4 读取、合并和裁剪

作业快照用同步 `jobs.list(caller)`，将 throw、查无、已终态分开；不用 `get` 的未知 id 抛错混淆故障和缺席。`stopping` 等尚未收尾的中间状态不当作终态，按未结处理。状态观察不推进输出游标。

一次返回只调用一次 `jobs.read(jobId, caller)`，避免提前消费输出。先按顺序拼接全部 channel 的 chunks 文本，再接首次终态 `result`。用 `result !== undefined` 判断结果在场；空字符串也是在场结果，不能按假值忽略。

```text
delta = chunks 中有效 text 按顺序拼接
body = 无 result ? delta : delta + 必要换行 + result
output = 终态状态提示 + lossy 前缀 + spill 线索行（读取视图报告 spillPaths 时） + truncate(body, maxResultChars)
```

合并和渲染按以下顺序处理：

1. 仅当 delta 非空且末尾不是换行时，在 result 前补一个换行。
2. 按真实终态 `completed`／`failed`／`killed` 添加状态提示。无输出或无详情也必须显示状态，中英两语都要完整。
3. 对合并后的正文实施一次 `maxResultChars` 裁剪：保留首尾，按原始内容计算省略量，标注 `truncated`。状态提示、`lossy` 前缀和裁剪说明另计。编排结算文本已有的状态及截断说明，不再被后续裁剪当作正文重新计算。首次等待与后台读取保持一致。
4. 若读取视图报告 `output.spillPaths`，在 `maxResultChars` 之外添加找回线索行（留存线索，即需求 9.3.4 的完整输出位置；单独计量，需求 2.2.3；spill 即宿主溢出留存——正文与 3.1 统一用「溢出留存（spill）」，涉及宿主键名时保留 `spillPaths` 原名）。读取视图指 `jobs.read` 回执的 job 字段／快照；路径只取宿主实际报告值，不判断文件仍完整或可读。无源留存、键缺席时不添加线索，也不声称有完整磁盘副本。

spill 清单的宿主契约是：按源序去重，无源留存时缺席，保存时间长于任何输出分块。因此读取位置低于 `earliest` 时，清单仍能说明字节写到了哪里。线索行中英完整，首次等待与后台读取一致，按需求 2.2.3 单独计量。

单一作业的返回正文按本节顺序合并；等待返回、首次等待返回与完成消息中的多作业条目共用 `maxResultChars`，按 2.6 的批次预算分配。展示开关（`workflowProgressLog`、`fullCommandEcho`，5.6 字段表）在裁剪之前筛选：可选内容先过滤，再进入合并与批次分配；退出码、失败原因、终止事实、读取失败、丢失、截断与留存线索不受开关控制。批次条目渲染与完成消息共用同一状态行形态（作业标识、终态、字符数，`lossy` 时附前缀）：无输出或无详情完成的作业在批次中以状态行可见，不因正文为空而从批次消失。

`jobs.read` 抛错时，返回独立的读取失败标记，不伪装成空输出。此时一次性结果尚未成功消费，之后可以重试。两个发现终态的分支共用这条读取路径。

`async_run` 和 `async_workflow` 首次等待内结果用启动闭包中的结算值，不为了直接返回而抢先消费注册表结果。后台句柄后由作业读取交付。

记录 shell 溢出留存（spill）文件路径，路径丢失且未报告时，明确说明没有找回落点。非零退出、信号终止和沙箱标记在 render 文本中可见，不能只存在于结构化 value。

### 2.5 返回提示的证据分级

`async_wait` 与两条首次等待路径的返回提示由真实可用证据选择整段内容；同一段提示里不允许既肯定目标运行、又称状态未证实。

- 两类陈述分开：「本次等待没有终止工作」是关于本工具自身行为的陈述，任何出口都可使用；「目标此刻仍在运行」是状态断言，只有当次观察（作业快照非终态、注册表 `running` 现读）证实才写进提示。
- 共享消息模板（`wait.wokeByMessage`、`wait.lateArrived`，`async_wait` 与首次等待路径共用）只陈述消息到达与正文将在领取点进入上下文，不内置运行断言；运行状态由随后的证据分档提示承担——证实仍在运行用 wait-again 提示，未证实换未证实提示（3.2 的两档）。消息模板只用于无目标等待的消息唤醒出口；有目标等待与首次等待不由非目标消息结束，不出现该模板。中英文两档同受本节约束（需求 5.3）。
- 取消出口使用取消口径：说明调用被取消、后台工作未因此终止，不使用消息到达文案。收件箱没有命中消息时，不得声称用户消息已到达或将进入下一输入；消息到达说明只由真实命中的消息出口使用。四类交回原因（消息、取消、预算到期、终态）的文案互不冒用（需求 2.1.2）。
- 首次等待路径的提前结束同受分级约束：插话、调用取消与目标结算提前结束时，完成优先复查的非终态快照支撑运行句柄文案；复查读不到快照时按未证实口径给出句柄与复查出路，不宣称命令或编排仍在运行。共享首次等待模板（含未证实档）的称谓按路径取「命令」或「工作流／编排」，不把编排误称命令（3.4 同口径）。迟到作答与一般通知不结束首次等待；作答正文按领取点进入上下文，首次等待返回值不为此改变口径。

### 2.6 交付批次与内容预算

作业内容直接交付给主体：完成时经完成消息或等待返回进入下一次模型输入，不要求模型专门调用工具领取（需求 9.3.2）。交付账本（`lib/delivery.js`）按主体登记交付事实并识别批次。本节适用于本包工具注册的命令与编排作业，以及挂载本包等待行的主体（本包预设或自建组合挂 `async_wait` 行）经宿主公开作业服务可见的其他作业——需求 9.3.2 以本包预设表述，本设计按工具行挂载口径同等适用（外来作业边界见 2.3）。

**领取窗口与批次识别。** 一个交付批次＝同一主体将共同进入下一次模型输入的本包交付内容集合；需求 9.3.2 的领取窗口按下列可观察事实识别：

- 等待类调用（`async_wait`，及 `async_run`／`async_workflow` 首次等待）的执行窗口内到达就绪的作业内容，并入该次调用的返回，同一批次。同拍（同一事件循环处理周期）并行发出的多个等待类调用汇入同一次模型输入，属同一批次：各返回从同一份批次预算分配，不因返回数分别取得完整预算（需求 9.3.2）。
- 无活等待时，作业结算由完成消息交付：账本向主体注入一条含结果正文的完成消息（`source.kind === 'async-tools-job-result'`，`form: 'notice'`），该完成消息本身即开启一个批次。注入之前回查主体 `nextStep` 与「本包待启动投递」登记——该登记是已构造完成、尚未经宿主通道发出的本包投递项清单（完成消息与迟到作答共用；投递成功即出登记，失败保留待重试或转 lost），完成消息经 `followup` 落 `nextTurn`、不在 `nextStep`，跨拍到达的并批判定以该登记为准：已有本包未领取的完成消息时并入同批，不再开启新批。
- 批在可观察的领取点关闭：主体的 `agent/inbox/claimed` 领取事件，或该主体全部本包活等待均已返回提交——并行等待以最后一个返回提交为准。关闭后到达的就绪内容进入下一批。

**在途仲裁。** 同一作业同时被等待返回与完成消息两路认领时，账本以先构造交付内容的一方为认领方（单线程事件循环内构造点原子置位），后到者只输出状态行。作业结算时若该主体存在本包活等待，完成消息路径让位——内容随等待返回交付；不存在活等待才注入完成消息。**让位终局复查**：等待返回提交、活等待注销时，账本复查未交付的就绪内容；该主体已无本包活等待时，另行注入完成消息交付，不等待模型主动领取。不存在「结算时让位、随后无等待却无任何交付载体（完成消息或某次返回）」的终局。

**批次预算与分配次序。** 同一批次内本包提供的全部结果内容共享一份 `maxResultChars`，即需求 5.2 的总内容预算（按 `String.length` 计量）；账本按主体维护当前批的剩余批次预算，逐个交付载体扣减，并行等待的多个返回不从新份分配。分配顺序：触发目标优先（有目标等待的目标作业）；其余按就绪时刻先进先出，同拍并列按作业 id 字典序。逐条顺序分配：每条取剩余批次预算与条目长度的较小值；单条超批次预算时按 2.4 的首尾保留裁剪。剩余批次预算为零后到达的条目整条延后。

**条目数与说明上限。** 单批交付条目至多 10 条，与宿主单主体并发出厂上限一致；超出部分延后并汇总一行说明（「另有 N 份结果延后」，附 `async_wait(targets=[…], wait_ms=0)` 供模型照抄的调用示例）。预算外说明（状态行、`lossy` 找回行、留存行、延后说明、截断标注）的总量按需求 9.3.2 给出有限且可测的规则：**单条说明至多 200 字符**——超长截断（宿主提供的留存路径、作业标识等外部字符串长度无界，200 字符在渲染层入界，`clampNote` 统一执行于批次条目状态行、批次条目 `lossy` 找回行、完成消息说明行与延后说明）；**单批逐条说明合计分两档**——状态行合计至多 2000 字符（条目上限 10 × 单条 200，批内每条作业恰有一条状态行，推导恒成立、无需运行时累计）；含 `lossy` 找回行（仅丢失条目携带，每条至多一行）的合计上界为 10 × (200 + 200) = 4000 字符，仍与内容预算同量级、不构成按说明绕开内容预算的通道；**单条完成消息内的留存行合计**受 2000 字符约束——超限保留状态行、留存行合并为一行计数汇总（`delivery.spillOverflow`，正文不受限）。数值固定可测，不随批内条目数放大。

**延后与继续。** 被延后的条目在账本中保留已消费未交付正文缓冲，下一批按先进先出优先交付；模型可随时用 `async_wait(targets=[{kind:'job', id}…], wait_ms=0)` 主动领取，零等待返回当前未交付内容与状态。

**防丢失与取消重叠。** 交付载体提交成功（消息注入回执、工具结果提交）才清空对应缓冲并登记已交付事实；已交付事实记录作业标识、终态与最近一次交付载体，首次等待返回、等待返回与完成消息共享同一份事实，并对后续一切交付路径双向阻断——已交付的作业不再进入批次候选、不再触发被动完成消息，再次等待只返回终态行与已交付事实（3.2.3）。读取成功但未进入本批（批次预算外、条目超限、等待取消）时缓冲保留，由下一个交付载体携带；交付批提交失败按真实装配退回缓冲与认领（回滚非空操作）。宿主读取游标与一次性 `result` 通道按宿主契约全局唯一：`jobs.read` 消费后正文由账本持有；游标推进不可逆，账本缓冲是已消费正文的唯一持有处。

**宿主与其他工具的正文不复制。** 判定只依赖可观察事实：其他读取方（如原生读取工具）已消费的正文，本包读取时只剩增量；宿主或子代理自行产生的消息（状态通知、转达、最终回答）保持原样，不计为本包重复投递，本包不对其做合并、改写或相似度去重（需求 9.3.3）。本包完成消息只携带尚未消费的正文；宿主状态通知与本包完成消息并存时，状态行不重复展开结果。

**与现有模块的接续。** 完成消息经 `followup`（主体空闲）或 `inject`（主体忙）进入收件箱，与迟到作答同一投递通道（[提问接管](<../lib/ask-takeover.js>) 的先例）；完成消息与迟到作答共用同一份「本包待启动投递」登记——同拍多作业结算且主体空闲时，各条完成消息合并为一条 `followup` 轮次投递，不逐条开启轮次。条目渲染复用 [输出](<../lib/output.js>) 的合并管线与两语词典（[模型文案](<../lib/text.js>)）；设置变更不重算已交付批次。账本随模块单实例驻留：同进程多插件实例各自持有账本，与刷新总线同一单实例前提；预设校验器核对单实例装配。两处接受性口径如实注明：①**清空点**＝交付内容构造点（单线程事件循环内原子），不是宿主提交回执点——宿主不提供提交回执，出口交付与工具结果提交之间存在微任务至毫秒级窗口，窗口内宿主把结果改写为取消错误时模型可能未见正文；该窗口的找回通道是宿主作业通知（保活链抑制撤销后照发）与 `async_wait` 重取（已交付事实在改写取消时不视为模型已见——undoClaim 只处理装配回滚，宿主改写不走账本）。②**行卸载**＝整体撤销：任一本包行卸载（disposeAll）清空全部行共享的账本与关批监听——账本按模块单实例驻留，行级局部撤销不成立；卸载后宿主原生作业通知照常，正文可经宿主作业面找回。

待核验对象：dsh `0.2.1-rc.4` 的 `@deepseek-ai/dsh-jobs-local` 读取游标与一次性结果标记在全部读取方之间的行为、`@deepseek-ai/dsh-agent` 的 `agent/inbox/claimed` 事件载荷与时机（领取点关闭批次的判定依据）、`@deepseek-ai/dsh-subagent` 消息 `senderSessionId` 契约。批次规则的全部判据以受控替身单测锚定，接线层用真实作业服务核对同拍结算与多载体并存。

## 3. 五工具与预设实现

### 3.1 命令作业

[命令模块](<../lib/jobs.js>)按以下顺序工作：入口主体／取消检查，解析参数和预算，解析沙箱并正常审批，审批返回后复查取消，取得有效目录并再次检查取消，解析执行后端并完成 bash 侧探测与受限包装（3.1.1），作业准入，在 starter 中启动 shell，首次等待，返回结果或句柄。

有效目录以目标宿主原生命令工具的 `workingDirectory.ensure(exec.agent, exec.signal)` 为基准：

- 入口要求调用主体。取得服务后，先 await `ensure`，再用返回的绝对目录解析本次 `workdir`：未指定时使用该目录，相对路径以该目录为基准，绝对路径保留。即使传入绝对路径，也先执行 `ensure`，与目标宿主原生工具的调用方式一致；具体目录访问和沙箱限制仍由宿主执行。
- `header.cwd` 是会话初始目录，不是可直接使用的当前目录。`working-directory/change` 通过投影记录后续切换，`ensure` 还包含目录存在性检查、当前目录失效后的恢复和同会话操作串行化；直读投影或 `workingDirectory.get` 都不等价。
- 服务缺席按 1.3 的固定依赖等待处理；服务方法不可用、目录检查／恢复失败或调用取消时，在作业准入及进程启动前返回可读错误或取消说明。不回退到初始目录、服务进程目录或投影直读，不因显式 `workdir` 绕过失败。目录恢复及对应通知由宿主服务负责，本包不另建恢复逻辑。
- 启动使用本次 `ensure` 和路径解析所得的目录快照。之后切换会话目录不改变已经启动的命令；调用等待结束也不再次解析目录或重启工作。

静态依据为 dsh `0.2.1-rc.4` 的 `@deepseek-ai/dsh-working-directory` 中 `ensure`／`set`／`serialize`，以及 `@deepseek-ai/dsh-tool-pwsh` 的 `resolveWorkdir` 和 execute。接口符号已按 dsh `0.2.1-rc.4` 安装树核实在场，实现逐项核读按 dsh `0.2.1-rc.4` 重新核验（待验证）；核读完成也不代表本包接线或运行行为已验证。

- shell 请求显式 `onExpiry:'none'`，不让宿主默认寿命定时器杀长命令；环境直接使用 `shellEnv.collect(exec)`。bash 后端在此之上向 resolve 请求附加 `env`（`TERM`／`LANG`，3.1.1）。
- 作业有确切 owner。注册名称（`label`，即需求 2.2.4 的任务名称）按完整命令回显开关的当前取值：开启时为命令原文，关闭时为 `description`；`description` 是活动期的进度说明，完成后按宿主行为清除进度。任务列表（宿主 `job_list` 逐行渲染 `label`）随注册名称呈现，开关关闭的模型输入中不含命令原文（5.6、8.2 展示开关行）；界面按原有权限保持可查的原始命令记录（含命令调用卡片）不受该开关影响（需求 9.3.4 第三条）。
- 输出缓冲预算为 `maxResultChars × 3` 字节；`maxResultChars` 按正整数校验（5.4），三倍换算恒为宿主 `outputLimitBytes` 要求的正安全整数。
- 注册拒绝按实际原因区分：并发触顶给上限、存活清单及出路，其余注册错误（含预算换算与宿主校验拒绝）原样可读上抛，不套用触顶文案。
- starter 内建立后台私有 AbortController，显式作业 cancel 才中止启动或停止进程。调用等待的 exec signal 不直连进程。
- 运行计时从批准后的启动阶段取得，不将审批计成命令已运行时长。首次等待的消息、取消和截止均不能丢失，消息已在待领取列表也有效。
- 准入拒绝发生在进程启动前，包含上限、存活清单及出路；shell 准备错误与并发拒绝区分。
- 结算按真实 proc 状态分 completed／killed／failed；done resolve 不自动等于 completed。输出 source 读取异常和 drain 守卫耗尽说明丢失。

首次等待的可见结果区分用户插话与调用取消：两者都只结束等待、返回作业句柄，已启动的后台任务继续由宿主作业管理；调用取消时宿主可能把可见调用结果改写为取消错误，此时句柄不一定到达模型。模型可经宿主 `job_list` 找回作业；转入后台的作业由保活链托管（2.3），结果经完成消息或等待返回直接交付（2.6），不因取消错误重新启动同一任务。工具描述须区分这两条路径，不把内部合法返回形状当作模型即时可见性的证明。`async_run` 与 `async_workflow` 的中英文描述采用相同边界，编排首次等待也按本段执行。

返回结构保持可校验：结算有状态、输出、truncated 和存在的退出／信号／detail；未结句柄含 `job_id`、耗时和原因说明。可选字段无值不写键，不填 DSL 不支持的 null。渲染必须覆盖每个返回分支——首次等待内 killed 无 signal、无丢失标记、无输出时，可见文本仍含两语 killed 终态提示，不得为空串（2.4 的无输出或无详情同样可见口径）。

显式提供 `workdir` 时，shell 准备失败给可读诊断（需求 2.1.3、5.7.2：错误说明当前原因、受影响对象及可行的下一步）。诊断有两个触发形态，共用同一套要素与同一核实结论：

- **拒绝形态**——`ctx.shell.execute` 拒绝、进程未建立，错误来自 shell 准备（shell 服务或执行器在进程建立前的失败）。
- **killed 形态**——目标宿主本地 shell 执行器的「进程未上报结局」契约：spawn 失败（如 cwd 缺失导致 spawn ENOENT）时 execute 照常 resolve 出进程句柄，句柄以 killed 结算、退出码与信号皆为 null，整条观测 stderr 流被替换为宿主注记 `subprocess failed before reporting an outcome: <原错>`（`@deepseek-ai/dsh-pwsh-local` 与 `@deepseek-ai/dsh-bash-local` 同款契约，README「A background provider-failure note is the whole stderr stream」）。检测信号取「宿主注记前缀＋无退出码无信号」的组合判定，以该宿主契约为出处，不解析注记内错误文本猜原因。

killed 路径只有同时满足以下条件，才附加目录诊断：真实终态为 killed、本次显式提供 `workdir`、输出中有宿主注记、没有退出码也没有信号。保留真实 killed 状态；宿主原错已经在注记中，不重复拼接。

拒绝路径与 killed 路径都在失败时刻用 stat 核实目录，再按同一张表选择诊断。不能从错误文字猜目录状态：spawn ENOENT 也可能来自可执行体缺席或权限问题。

| stat 核实结果 | 诊断结论 |
| --- | --- |
| ENOENT／ENOTDIR | 目录不存在。 |
| stat 成功，路径是目录 | 目录存在，失败原因在别处。 |
| stat 成功，路径不是目录 | 路径已存在但不是目录；`workdir` 必须指向目录。使用 `error.workdirPrepNotDirectory` 的 en／zh 文案，五要素模板其余不变。不能引导读者去查别处的原因。 |
| 其他核实失败 | 目录状态未证实，保持不确定。 |

诊断保留真实原错与真实终态，附请求的 `workdir` 原值、按会话当前有效目录解析后的绝对路径、会话当前有效目录本身；出路给可行动作：修正 `workdir` 后重试、先核实目标目录。不把一切 ENOENT 断言为目录缺失，不静默改在其他目录执行。

出口一致性：首次等待与注册表后台结算两条出口同一文本、两语言一致。作业结局的 killed 分支是同步函数而 stat 核实是异步——诊断作为 killed 结局的异步后处理接在两处出口：注册表结算的 done 钩子本就返回 Promise，后处理并入其链；首次等待的即时结算（settleNow）返回 Promise，由 async execute 展平。拒绝形态沿用同一文本进入首次等待的原样重抛出口与后台读取的 `detail` 拼装（2.4）。词典键 `error.workdirPrep` 两语，占位为请求原值、解析绝对路径、会话当前目录、核实结论、出路；拒绝形态的真实原错以原文独立拼接进诊断、不进占位模板。

边界：缺省 workdir 不加诊断（无新信息）；prep 窗口被中止的 killed 形态（execute 未 resolve、进程未到位，按中止归类结算）不套用此诊断，按 killed 口径原样呈现——它与「进程未上报结局」形态的区分正是进程句柄是否到位：中止形态进程未建立，未上报结局形态 execute 已 resolve、注记已在输出中。spawn 窗口内的显式取消同属中止形态：execute 拒绝、进程句柄未建立，输出中没有宿主注记，不命中 killed 形态的检测信号。进程句柄是否到位只是与中止归类的区分点，不是 killed 形态的判定依据——判定始终以「宿主注记前缀＋无退出码无信号」为准，句柄已到位而带退出码或信号的 killed（如显式终止）同样不命中。

#### 3.1.1 命令行后端选择（GB-01）

Windows 会话可把 `async_run` 的默认命令行从 PowerShell 切到 Git Bash。后端选择只作用于本包 `async_run`（子代理组合挂载的 `async_run` 行按同一规则解析）；`async_workflow` 只编排代理、不经 shell 执行命令，不参与本节。需求依据为需求 9.2；执行、等待与交付的其余机制（第 2 章与 3.1 正文）不随后端改变。

**受限令牌可行性裁定（需求冲突）。** 本节管线的前提——bash.exe 在 windows-acl 受限令牌下可运行——已实测裁定不成立。2026-10-30 经 DSH 受限沙箱实测（`async_run` 工具进程；实测于 write-restricted＋Low 完整性档，read-only 为同族令牌构造）：Git 安装根 `bin\bash.exe` 与 `usr\bin\bash.exe` 两形态以 `-c` 执行简单命令，均退出码 1、同一错误——`cygheap_user::init: NtSetInformationToken (TokenDefaultDacl), 0xC0000022`，随后 `couldn't create signal pipe, Win32 error 5`；同机同安装对照（danger-full-access 非受限令牌）正常执行，`uname -s` 返回 `MINGW64_NT-10.0-26100`——Git 安装本身可用，失败原因是受限令牌。机理：MSYS2 运行时启动时自调令牌默认 DACL，被 write-restricted＋Low 完整性令牌构造拒绝，与 dsh-sandbox-windows-acl 的令牌构造机理冲突。需求 9.2 要求 Git Bash 在只读、工作区内读写及自动审批预设下直接运行当前策略允许的命令，恰是受限令牌档位——该要求在本部署不可满足。实测构成需求冲突。

**技术规避调研（2026-10-30 本机三组实测；用户指定核查 dsh-ops，`https://github.com/T-Auto/dsh-ops`）。** A：dsh-ops 的定制 MSYS2 运行时（npm 包 `@dsh-ops/bash-win32-x64@0.2.1`，提取 `bin\bash.exe`＋`usr\bin\bash.exe`＋`usr\bin\msys-2.0.dll`＋`cygwin-console-helper.exe` 最小集）在受限令牌下执行 `-c`，死于与 Git Bash 逐字相同的错误（退出码 1，`cygheap_user::init: NtSetInformationToken (TokenDefaultDacl), 0xC0000022`，随后 `couldn't create signal pipe, Win32 error 5`）——cygheap 初始化与受限令牌的冲突覆盖 MSYS2／cygwin 家族，运行时替换方向已排除。B：dsh-ops 源码核读（`src/shells/execution.ts` 的 `startBashExecution`）——其 `ops_bash` 直接 `subprocess.spawn`（宿主子进程服务），不经 dsh-shell 的 `execute`／`executeArgv` 链、不构造受限令牌，实为绕过宿主 shell 沙箱链运行 bash，等价于「仅非受限档生效」形态，不是受限档内的规避。C：busybox-w32（frippery.org 官方 `busybox64u.exe`，683,520 字节，纯 Win32 API、无 cygwin 依赖）在受限令牌下正常（`uname -a` 与 `echo` 均返回），但其 shell 是 POSIX ash 兼容子集而非 Git Bash（无 MSYS 路径翻译与 GNU 工具全集）。结论：受限档内运行 Git Bash 的技术规避不存在。

**裁定结果与暂停状态。** 实测与技术规避调研经两轮上抛后，用户裁定（2026-10-30）：路线为「非受限档运行＋如实标注」——若实施，bash 仅在 danger-full-access 档运行（含经 6.1 单次提权获批进入该档的调用）；受限档（经 confine 的 read-only、workspace-write）下开关开启、本次有效后端为 bash 时，按可读错误返回并给提权指引（6.1），零作业注册、零进程启动，不降级执行、不改走 pwsh；工具描述与字段帮助如实标注该限定；需求 9.2 的对应改写在实施轮完成。当前状态为暂停待重启：不进当前交付、不实施、不销毁设计材料；恢复实施前需经一轮全新盲审并完成需求 9.2 改写。本节其余内容与 5.5／5.6 字段帮助、`async_run` 描述文案保持完整，作为恢复实施时的设计依据；其中受限包装、审批等价与沙箱事实盖章各段的受限档形态，以及 5.6 字段行与描述要点中的执行语义，均按上述裁定路线取用并如实标注非受限档限定，实施轮随需求 9.2 一并改写。

**后端解析。** 每次调用现读解析，不跨调用缓存：

| 输入 | 取值 |
| --- | --- |
| 单次参数 `shell` | 可选枚举 `bash`／`pwsh`，给出时优先于设置；未知取值经 schema 枚举按参数校验拒绝 |
| 设置 `gitBashShell` | 布尔，默认关（5.6 字段表）；开启且平台为 win32 时默认后端为 bash |
| 平台 | win32 默认 pwsh；其余平台默认 bash（宿主根组合装载的执行器即 bash 家族） |

- 有效后端等于平台默认时走现行 `ctx.shell.execute` 路径：win32 的 `pwsh` 与非 win32 的 `bash` 都不引入本节管线（非 win32 的 `ctx.shell` 本就是 bash 执行器，`shell: 'bash'` 与省略等价）。
- win32 下有效后端为 `bash` 时走本节管线。
- 非 win32 下显式请求 `pwsh` 按可读拒绝：该平台组合没有 PowerShell 执行器，指引省略参数按默认执行；零作业注册、零进程启动。
- `shell` 参数与 `gitBashShell` 设置在两个方向都可选（开关在 PowerShell 时单次选 bash，开关在 Git Bash 时单次选 pwsh）。`async_run` 的描述随设置重建，写明当前默认命令行与单次参数用法，两语一致。
- 作业启动时绑定本次后端、命令与权限；此后切换设置或参数不改变已启动作业的后端与权限。设置保存后后续新调用立即采用新值（与 5.1 同一条生效链）。

**执行管线（选型）。** win32 的 `ctx.shell` 是宿主根组合装载的 PowerShell 受限执行器（dsh-base 根补丁的 `pwsh-sandbox` 行；`bash-sandbox` 行在 win32 禁用，`tool-bash` 工具行同样禁用）；cordis 一个 context 只装载一个 `shell` 实现，装载第二个抛错。三个方向不可行，先行排除：

- 组合切换装载（在组合里装载 bash 执行器行）：执行器行在根组合、全进程一份，切换影响全部会话与全部工具的命令执行，且设置保存无法即时改变已装载组合——与「仅影响本包 async_run」「保存后立即生效」两条要求冲突。
- 插件绕开 `ctx.shell` 自管 subprocess 管线：须重实现输出收集、溢出留存、kill、grace、deadline 与「进程未上报结局」注记等执行器语义，等价论证与维护负担最大，也与需求 1.2「不替换宿主的命令执行服务」的边界冲突。
- 命令经 pwsh 启动 bash（`pwsh -Command "bash -c …"` 包装形态）：受限单元与审批身份都落在 pwsh 包装上，引号与编码多层嵌套，拒绝分类与输出语义偏离最远。

选定方案：**调用现役执行器的 `executeArgv` 扩展点**。宿主两个本地执行器（`dsh-pwsh-local`／`dsh-bash-local`）的 `executeArgv(spec, argvOrPrepare, onStarted?)` 均为 `protected` 实现接口——文档定位为「子类在执行边界替换公开命令的 shell argv 后使用」的扩展点，宿主自己的受限子类（`dsh-pwsh-sandbox`／`dsh-bash-sandbox`）正是在这里经 `ctx.sandbox.confine` 包装 argv。本插件在调用侧做同一件事，是对该 `protected` 实现接口的跨边界消费，不装载第二个执行器、不改组合：

```text
spec = ctx.shell.resolve({ command, workdir, dshEnv, sandboxPolicy,
                          onExpiry: 'none', env: { TERM: 'dumb', LANG: 'C.UTF-8' } })
bashExe = 覆盖或探测（「探测与覆盖」段，准入前完成；失败零作业注册、零进程启动）
argv = [bashExe, '-c', spec.command]
policy.mode ≠ danger-full-access 且 ctx.shell.sandboxMode ≠ undefined 时：
    prepared = await ctx.get('sandbox').confine(argv, policy, exec.signal)
    argv = prepared.argv                      # runner 前缀 + '--' + argv 逐元素透传
starter：ctx.shell.executeArgv({ ...spec, signal: 作业私有 signal }, argv, onStarted)
```

- argv[0] 用覆盖或探测出的绝对路径，不用裸名 `bash`：PATH 上的裸名可能解析到 WSL 的 `System32\bash.exe`——另一个运行时。宿主 bash 执行器用裸名是其 Linux 主场的部署事实；本插件在 win32 显式给绝对路径。
- `ctx.sandbox.confine` 与宿主 bash 执行器同源：同一 `ctx.sandbox` 服务、同一 windows-acl 受限令牌 runner、同一 policy 解析。bash 及其子进程都在受限令牌下运行，工作区外写入由 OS 层拒绝；confine 失败时原样抛出（含 `SANDBOX_UNAVAILABLE`），不静默改走未隔离执行。bash.exe 在该令牌下的可运行性见本节「受限令牌可行性裁定」（已实测裁定失败）。
- `resolve` 仍走现役执行器：超时、输出预算、溢出留存上限、grace 等生命周期配置继承组合现值，两条后端同源。confine 在作业准入与进程启动前完成（属参数准备段，与 `workingDirectory.ensure` 同层），失败时零作业注册、零进程启动；产物 argv 随 spec 交给 starter。
- `spec.env` 在执行器 spawn 合并序（执行器环境覆盖 → `spec.env` → `spec.dshEnv`）中优先于执行器覆盖项：`TERM=dumb` 抑制交互终端特性（与宿主 bash 执行器的环境覆盖集保持一致——pwsh 集不含 TERM），`LANG=C.UTF-8` 稳定 UTF-8 输出；`dshEnv`（`shellEnv.collect`）不受影响，不追加、不剥离键（需求 6.2）。
- `executeArgv` 不在 `ShellExecutor` 抽象契约内（dsh-shell 契约含 `execute`／`resolve`／`sandboxMode`，不含 `executeArgv`），是两个本地执行器的 `protected` 实现接口，本包跨边界消费。稳定性风险——宿主后续将其改私有、重命名或移位——以下列方式承接：调用前现读检查 `typeof ctx.shell.executeArgv === 'function'`；缺席时 bash 后端按可读失败处理（该组合的 shell 执行器不提供命令行切换），零作业注册、零进程启动，不改走 pwsh；支持集合调研时三个 rc 的两个本地执行器均带该接口（rc.5 加入集合后未重开本项调研），逐 rc 静态核读（待核验）。
- `ctx.get('sandbox')`／`ctx.get('sandboxPolicy')` 为运行时可选读取（与 6.1 提权接线同一模式），不进九项固定声明；受限执行器装载即保证 sandbox 服务在场，读不到时按可读失败处理。

**沙箱事实盖章。** 宿主受限执行器在结算钩子给受限进程写 `proc.sandbox`（`{mode, denied, enforcement, runnerFailed?}`），3.1 的沙箱标记管线（`sandboxMarkers`）消费 `denied`。经 `executeArgv` 启动时宿主不替本包写章（其事实表只登记自己 `execute` 发起的进程），由本包在 `onStarted` 回调登记 confine 事实（`enforcement`、`denialSignatures`、`runnerFailureRules`、runner 程序），并对 `proc.done` 挂一次盖章回调：结算后按 `proc.observed.stderr.readFrom(0).text`（非消费偏移读，不与作业泵抢字节）与 `proc.exitCode`，用 `@deepseek-ai/dsh-sandbox` 公开的 `classifyRunnerFailure`／`matchesSignature` 分类，写入同形状 `proc.sandbox`。runner 失败（exit 127 加 `windows-acl-run: ` 前缀一类）按 `runnerFailed` 记录，不冒称命令拒绝，也不静默当成功。provider 拒绝分支（runner 本体 spawn 失败：execute 已 resolve、句柄以 killed 结算、观测 stderr 为宿主注记文本）不写 sandbox 章，按 3.1 既有 killed 出口与宿主注记路径呈现，`sandboxMarkers` 在该分支不触发：宿主受限子类在 `onProcessDone` 的该分支以结构化 `providerError` 调 `isRunnerSpawnFailure` 写 `runnerFailed` 章，本包在该分支可读的只有注记文本与退出码，而 `isRunnerSpawnFailure` 的输入是结构化错误对象（`typeof error !== "object"` 即拒绝），注记文本形态恒返回 false——同形状 `proc.sandbox` 在该分支不可实现；不解析注记内错误文本猜原因，与 3.1 同一纪律。`onStarted` 在 `executeArgv` 返回前同步执行，盖章回调的注册先于作业结算链——结算消费（首次等待的即时结算与注册表 done 钩子）读 `proc.sandbox` 时章已写好；该时序以单元装置断言（8.2）。未 confine 的调用（danger-full-access、非约束组合）不写章，与宿主执行器口径一致。

**非约束组合的镜像。** `ctx.shell.sandboxMode === undefined`（现役执行器不沙箱化）时，pwsh 路径本就不受限、不暴露提权字段；bash 路径同样不 confine，直接以 `[bashExe, '-c', command]` 经 `executeArgv` 执行。开关不授予权限：同一组合下两条后端受同一策略约束。

**探测与覆盖。** `bash.exe` 的解析按下列优先级逐级回退，全部失败才报错：

1. 覆盖字段 `gitBashPath`（非空时）：接受 bash.exe 完整路径或 Git 安装根目录——stat 判别，目录依次试 `bin\bash.exe`、`usr\bin\bash.exe`，文件直接使用。字段值无效时按可读错误返回（含字段原值与出路：修正字段或清空改走自动探测），不改走自动探测——用户显式给的路径失效时静默换路径会掩盖问题。
2. 环境变量 `GIT_INSTALL_ROOT`（设置且其下 `bin\bash.exe` 存在时采用）。
3. 常见安装位置 stat 验证：`%ProgramFiles%\Git\bin\bash.exe`、`%ProgramFiles%\Git\usr\bin\bash.exe`、`%ProgramFiles(x86)%\Git\bin\bash.exe`、`%LOCALAPPDATA%\Programs\Git\bin\bash.exe`。
4. `PATH` 逐项拼 `bash.exe`，排除 `System32`／`SysWOW64` 项（WSL 的 bash.exe 不认）；stat 命中后做身份探测确认是 Git Bash——`<候选> -c "test -n \"$MSYSTEM\""` 退出码 0（Git Bash 设 `MSYSTEM`；WSL 与 Cygwin 不设）。探测经 `spawnSync`，超时 5000 ms（与宿主沙箱探测同值），失败或超时跳过该候选继续。

PATH 候选的身份探测结论按候选绝对路径在进程内缓存（路径固有属性；覆盖字段不进缓存）。自动探测无可用候选时按可读错误返回：说明未找到 Git for Windows、给出官方安装指引（`https://git-scm.com/download/win`）与 `gitBashPath` 覆盖出路；零作业注册、零进程启动，不随包分发运行时。探测与覆盖解析都发生在作业准入与进程启动前；`exec.signal` 已取消时中止探测，按取消口径返回。

**审批等价。** 提权接线（6.1）不随后端改变：字段对校验、严格加宽判定、`approveEscalation` 顺序、许可仅作用本次、拒绝与取消零启动都与 pwsh 路径同一条链。审批请求携带真实工具身份（`async_run`）、主体、调用标识与理由；命令原文经调用卡片与作业注册可见——审批方（含 `dsh-approve-for-me` 按其生效配置的自动审批）看到的是实际将执行的 bash 命令与实际参数、工作目录、申请权限及理由，不是无实际内容的启动包装。策略允许的普通命令直接以当前策略运行，不因后端为 bash 而要求提权。获批后的更宽 `policy.mode` 流入本次 `confine`；拒绝、取消或审查故障时零启动，不执行所申请的越权操作。同一会话策略与审批配置下，pwsh 与 bash 的等价操作可审批性一致：受限写入两者都得到沙箱拒绝标记（同一 `denialSignatures` 分类），需要更宽权限的操作两者都经同一提权审批送审。

**输出与退出码。** bash 输出按 UTF-8 解码（`LANG=C.UTF-8` 覆盖多数工具；宿主 collect 管线的解码假设列为待核验）。`bash -c` 的退出码即最后命令的退出码（0–255；127 命令不存在、126 不可执行——windows-acl runner 失败的 127 经 `runnerFailed` 分类区分，不混淆）。路径形态：spawn 的 `cwd` 是 Windows 绝对路径，bash 内以 `/d/…` MSYS 形态呈现，命令内相对路径直接可用；绝对路径 `/d/…` 与 `D:/…` 两种形态都可用，反斜杠是转义字符。中文与空格路径经 argv 逐元素传递（confine 后 `--` 逐元素透传，无引号层）。描述在后端为 bash 时给模型 POSIX 语法与路径形态指引。

**静默失败防线的后端适用性。** 6.2 的签名 1（捕获形加空输出的条件提示）锚定本部署受限 PowerShell 在进程创建层击杀捕获形命令这一部署事实；bash 后端下该事实不成立，签名 1 仅在本次执行后端为 pwsh 时参与判定（`silentFailureNotes` 增加 backend 判定输入）。bash 后端的空输出更可能是命令本身无输出，不给「可能未执行」提示；受限拒绝的主标记走 `proc.sandbox.denied`（大小写不敏感的 OS 层签名，覆盖 GNU 工具的 `Permission denied` 形态），签名 2 的锚对保持现状（pwsh 部署实测文本），漏报不构成缺口。描述警示与纪律段（6.2 另两处）不随后端变化。

**失败路径。**

| 阶段 | 失败形态 | 处理 |
| --- | --- | --- |
| 后端解析 | 非 win32 显式 `pwsh` | 可读拒绝，指引省略参数按默认执行；零作业注册、零进程启动 |
| 后端解析 | win32 受限档（经 confine 的 read-only／workspace-write，见节首裁定）下有效后端为 bash | 按裁定路线（节首「裁定结果与暂停状态」）：可读错误＋提权指引（6.1）；零作业注册、零进程启动，不降级执行、不改走 pwsh |
| 参数校验 | `shell` 枚举外取值 | 参数校验拒绝 |
| 覆盖字段 | 值无效（路径不存在、目录下无 bash.exe） | 可读错误：字段原值＋修正或清空的出路；零作业注册、零进程启动 |
| 自动探测 | 无可用候选 | 可读错误：安装指引＋覆盖字段出路；零作业注册、零进程启动 |
| 探测取消 | `exec.signal` 已取消 | 按取消口径返回 |
| 受限包装 | `SANDBOX_UNAVAILABLE` 或授权物化失败 | 原错单行化可读上抛，说明受限执行不可用；不改走 pwsh、不未隔离执行；零作业注册、零进程启动 |
| 启动 | spawn 失败 | 既有 killed 与「进程未上报结局」注记契约（3.1），诊断路径不变 |
| 运行 | runner 失败 | `runnerFailed` 事实加可读失败说明，不冒称命令拒绝 |
| 运行 | 沙箱拒绝 | `proc.sandbox.denied` → 拒绝标记＋提权提示（现有管线） |

**与交付机制的接缝。** proc 句柄与 pwsh 路径同族（`observed`／`readOutput`／`kill`／`done`／退出码与信号），作业注册、首次等待竞速、保活链、交付批次与完成消息（第 2 章）零改动；注册名称按完整命令回显开关取值（3.1），命令原文即 bash 语法文本。

**待核验。** 调研时支持集合三个 rc 的 `dsh-pwsh-local`／`dsh-bash-local` 中 `executeArgv` 符号与静态 argv 形态（rc.5 加入集合后未重开本项调研）；插件上下文 `ctx.get('sandbox')`／`sandboxPolicy` 可达性；`spec.env` 在现役 pwsh 执行器 spawn 合并序中的优先级；宿主 collect 管线的输出解码假设（UTF-8）；`TERM=dumb`／`LANG=C.UTF-8` 对 Git Bash 工具集的实际效果；显式 kill 与 teardown 对受限 runner 及其 bash 子进程的停止语义；盖章回调先于结算消费的注册顺序。核验方法：逐 rc 安装树静态核读符号与合并序；单元装置断言时序与解码；停止语义与真机行为按 8.2 的 Windows Git Bash 后端装置行执行。

### 3.2 统一等待

`lib/wait.js`（统一等待）是唯一的等待入口：`async_wait` 以一份预算支持无目标等待与多目标等待，`async_run`／`async_workflow` 的首次等待以刚创建的作业为目标，复用同一竞速编排（第 2 章的总截止、消息集合、入口扫描与交付批次）。首次等待的唤醒条件与有目标的 `async_wait` 相同：目标作业终态或用户插话结束；非目标通知不提前结束（2.2）。

#### 3.2.1 参数与校验

参数两个：

- `wait_ms`：必填数值。有限且非负才有效（`Number.isFinite` 且不小于 0）；负值、非数值经参数校验按可读拒绝返回，不进入夹紧。正数按需求 5.2 上下限夹紧；0 是合法取值，不夹紧到 `minWaitMs`，按零等待口径执行（2.1）。
- `targets`：可选数组，元素形状 `{ kind: 'job' | 'agent', id: string }`。省略与空数组等价，都表示无目标等待。schema 以数组元素对象组合表达——参数表声明 `targets` 为 array、元素为 object（`kind` 枚举、`id` 字符串），由宿主 `defineTool` 的参数 spec 编译成模型侧 schema，示意：`{ type: 'array', items: { type: 'object', properties: { kind: { type: 'string', enum: ['job', 'agent'] }, id: { type: 'string' } }, required: ['kind', 'id'] } }`；枚举与形状由 schema 挡第一层。execute 入口再做语义校验：`id` 为空串或全空白、`kind` 不在枚举内按可读拒绝；重复项按同一目标去重，不报错。

#### 3.2.2 目标判定与存在屏障

入口先对每个目标做存在性判定，查询失败与查无分开（需求 9.3.1）：

- 作业目标经同步 `jobs.list(caller)`：命中行＝存在，非终态与终态行都算存在，终态走 3.2.3 的终态入口；查无＝该主体可见清单中没有此 id（含其他主体的作业，宿主按 caller 过滤）；查询异常＝查询失败。查无按可读拒绝返回并提示宿主 `job_list`；查询失败按可读拒绝返回并给重试出路，两者不互为文案。
- 子代理目标先证合法关系（本主体的子代理），再查公开注册表。关系判定经 `subagents.listChildren(parentId, signal)`：目录行命中＝存在；查无＝可读拒绝并附已知子代理清单；查询失败＝可读拒绝并给重试出路。屏障重试沿用 2.1 的三拍与预算纪律；零等待只发起一次，未回即按存在性未定交回。

#### 3.2.3 作业目标适配

作业目标的状态三分与读取按 2.4：入口即终态时读取一次交付（含一次性 `result` 与增量，游标推进由读取承担）；运行中进入等待——事件通道（`jobs.wait` 到期或结算释放；非终态到期 resolve 后同步续排，与 2.3 的保活链同机制）与快照复核并行，等待中终态证据先到即按终态结果返回。已交付终态的目标再次等待：入口终态读取照常执行（消费一次性通道防丢失），但批次装配被已交付事实阻断——触发目标与批次候选都不再携带正文，返回只含终态行与已交付事实，同一最终结果在正常交付中只出现一次（2.6）；完成消息已投的作业再次等待同口径。读取失败不写成空结果或已交付，保留读取失败标记并给重试出路（2.4）。运行中目标以零等待读取时返回当前增量与状态；无新增内容时明确说明，不把无增量解释为任务失败。

#### 3.2.4 子代理目标与变化通知

子代理目标适配（`lib/wait-agent-target.js`）先用公开目录确认调用主体与目标的合法关系，再查公开 Agent 注册表取当前运行状态；合法关系判定与运行状态判定分别由 `subagents.listChildren` 与 `agents.get(id)` 承担，无驻留 Agent 与目录不存在分开。

入口检查在目录命中后查 `agents.get(agentId)`，结果与观察基准（下段）的跨调用登记比较：

- 命中且 `status !== 'running'`：按跨调用比较处理——登记为运行（发生未报告的翻转）或无登记（首次确认）时，立即返回停止态结果，说明停在「状态转为 idle」，不空等、不冒称成功；登记已是同态静止（已向本主体报告过的空闲）时不重复交回，进入等待新变化。
- 命中且 `running`：登记为空闲／无驻留（恢复运行）时立即报告一次变化；无登记或登记为运行时进入等待。
- `undefined`：注册表无驻留，读作「不再观察到它在运行」，与目录行消失同档处理（比较规则同首条）；不据此宣称子代理已终结。
- 查询抛错：状态未证实，不制造 not-found 也不制造停止态。

等待子代理＝等待需要本主体处理的变化，不是收集结果（需求 9.3.3）。变化证据有三类，返回只携带说明，不复制正文：

1. 目标发给本主体的未领取可处理消息（普通转达、提问、结算通知），按 `senderSessionId` 精确匹配；发送者不匹配任何目标的消息按 2.2 的无目标规则处理，不改变目标状态。
2. 公开状态事件或现读能证明的状态转换（`running` 转 `idle`、静止后恢复 `running`）。
3. 结算通知：关系与停止证据齐备，按 `settled` 返回。

观察基准分两层（需求 9.3.3）。**跨调用登记**：子代理目标适配模块（`lib/wait-agent-target.js`）按「主体×目标」登记最近一次已向该主体报告的公开状态（运行、空闲或无驻留）——向主体交回该目标的状态或变化说明时更新，状态翻转时覆盖，目标经存在屏障确认查无时清除；登记只存状态，不存消息正文，不缓存 `settled` 结论，目标恢复运行即按翻转处理。**本次调用比较**：入口可观察状态与该登记比较——查到静止（`idle`／`absent`）且登记为运行是未报告的翻转，查到静止且无登记是首次确认，两者都按停止态立即返回一次；查到静止且登记同态是已报告的静止，不重复交回同一停止态，进入等待新变化，到期无新变化按到期口径交回并说明目标维持已确认静止；查到 `running` 且登记为静止是恢复运行，立即报告一次变化；无可比较观察（存在性未定）时基准为空，任何可证新变化都可交回。目录中存在记录本身不算变化；已报告过的变化（已领取消息、已交回的变化说明）不再唤醒本次等待；静态状态（持续 `running` 且无新消息）不构成变化。调用内观察记录只存事实三元组——状态、观察时刻、是否已报告——不存消息正文。

先到消息出口同受合法关系优先约束（需求 2.3.3）：停止态、查无与「最终回答将另行到达」类投递承诺，一律以合法子代理关系为前提——父会话目录行，或 `senderSessionId` 精确命中结算通知的等价投递证据；关系未证明时，注册表读数（`idle`／`absent`）不是停止证据，无关主体在注册表中的状态不构成本次等待的断言。入口扫描命中先到消息（user 插话、notice／relay、本包迟到作答）时按下列次序处理：

- 未领取的权威结算通知最先交回：`senderSessionId` 精确命中的结算通知由宿主投给父主体，投递本身即关系证据，无需目录查询（2.2）。
- 现读注册表一次作同步分档：`running` 不发起目录查询，直接按消息口径交回——user 插话 interrupted、其余运行句柄＋唤醒／迟到原因，运行句柄文案取 2.5 的证实档；`unknown`（注册表读取抛错、状态未证实的统称）同口径交回，文案取未证实档，不作运行断言。
- 读到 `idle`／`absent` 是停止候选：先发起关系定性查询（`listChildren`，经同一在途目录查询通道——主循环内在途至多一路，2.1），与工具取消、等待中新到信号（唤醒／迟到作答）、定性窗口、总截止竞速。先到消息在这条分支里已被消费，不再是竞速成员——先到的唤醒不解析 `interrupt.promise`，定性窗口就是这条消息的唯一出口。窗口因此取 `min(pollIntervalMs, 剩余预算, 2000 ms)`——默认配置下窗口仍由轮询间隔决定（500 ms），只有更大的轮询值被压到上限。2000 ms 的固定响应上限为慢而健康的目录留出至多四倍于默认间隔的定性机会，并给 8.1 的 5000 ms 响应窗保留六成余量给宿主调度与观测开销。三条先到路径（user 插话、本包迟到作答、notice／relay）统一适用。先到消息至多等待一个定性窗口，不为定性查询等满剩余预算（需求 2.1.2）。剩余预算不小于上限时，窗口由固定上限封顶，在 8.1 响应窗内交回；轮询间隔或剩余预算小于上限时窗口随之缩短。窗口先于截止耗尽，或剩余预算成为三者最小值而与总截止同拍收场，都按窗口耗尽档的消息口径交回。窗口计入总预算。查询结果四档分开表述，不得互相冒充：
  - 返回目录行——关系已证明：现读注册表复核，仍为 `idle`／`absent` 才按停止态结果返回（`idle`＝状态转为 idle，`absent`＝无驻留），并存消息以附加说明表达、正文留给宿主领取；复核变为 `running`／`unknown` 则回落消息口径。
  - 查无该 id——单次查空不构成「从未存在」的断言（与屏障重试同一理由）：按存在性未定交回，user 插话 interrupted、其余运行句柄＋未证实口径；查无断言与已知子代理清单由下一次调用的存在屏障交付。
  - 查询失败——不是查无，也不是停止：同存在性未定口径交回，给重查出路。
  - 窗口耗尽／取消／新信号先到——窗口耗尽按消息口径交回（关系未证明，未证实档）；取消按取消口径；新信号先复核未领取结算通知（完成优先），再按先到消息的类别交回（先到 user 不被后到 relay 降级，反之亦然），存在性留给下一次调用。
- 弃用的定性查询与清单查询的迟到结果、拒绝都必须承接，不悬挂资源、不遗留未处理拒绝（2.1）。注册表复查是同步现读；不用消息到达制造「目标仍运行」的事实。

- `running` 表示驱动在运行，`idle` 表示当前无驱动；不据此推断成功。目录中的 catalog 存在不证明仍运行，descendant 的驻留 activity 也不能替代这一状态。
- 等待中双通道并行：事件通道（`agent/status` 转 idle、目标结算通知）与轮询通道（按轮询间隔查 `agents.get(agentId)` 的 `status`）。轮询不只查目录行消失；注册表无驻留与查询失败在轮询里同样分开，失败不触发结束。

事件通道须保存权威事件及其目标身份，`agent/status` 载荷按目标 id 匹配，不能只存一个无名标签。判断能否结束等待时，先分清两类证据：

| 证据 | 证明什么 | 取得方式 |
| --- | --- | --- |
| 关系证据 | 本主体有权等待该目标 | 本次 `listChildren` 返回命中 id 的非诊断目录行；或本主体未领取的结算通知，其 `senderSessionId` 精确命中目标 id。通知已投给父主体，本身即证明关系。 |
| 停止证据 | 目标当前不再运行 | 上述结算通知、目标 `agent/status` 转 idle 事件，或注册表 `idle`／`absent` 现读。 |

按证据决定动作：

- **收到精确匹配的结算通知**：关系与停止两类证据齐备，可直接交付 `settled`。
- **关系已证，收到 idle 事件或读到 idle／absent**：按「观察到停止」返回 `settled`，不必等结算通知；通知缺席或迟到不削弱权威 idle 证据。
- **关系尚未证明**：idle 事件与 idle／absent 读数只登记，不返回 `settled`，不承诺最终回答另行到达。存在性检查挂起、查询失败或尚未确认查无时，都属于这一档。等待仍受同一总预算约束；取消、可处理消息及时交回，到期按存在性未定交回。
- **随后取得关系证据**：目录行返回或结算通知投递后，本次调用内已登记的停止证据立即生效，不要求事件重发。

事件可见不等于有权等待。`agent/status` 按作用域发布，但同一组合下兄弟作用域的事件也可能被本包监听器收到；目标宿主作用域装置已证实这一点。同 id 事件因此不能独自证明父子关系。

`settled` 只说明当前观察到目标停止，不说明成功或最终回答已经送达；回答仍按宿主消息另行进入上下文。

- 可靠停止证据（结算通知、注册表 `idle`／`absent` 现读、状态转 idle 事件）在手的返回立即交付，不被顺带目录复查拖延：目录复查只是弱证据的顺带升级，不作为返回前置。收敛后的复查与取消、消息和到期同时竞速（2.1），宿主查询忽略取消信号时取消仍立即交回（即时性判据 8.1）；迟到到达的复查成功与拒绝都有承接，不悬挂资源。
- 已经停止的目标入口直接交回，当前运行的目标订阅状态和结算，并在总截止内按轮询间隔重查。
- 目录查询失败不进入 not-found，状态未知不制造成功。查无出口（存在屏障重试确认后）附已知子代理清单；清单查询是可选诊断，与工具取消、等待中新到信号、权威停止及总截止竞速：取消先到按取消口径、消息先到复核结算通知后按消息口径、权威停止先到按停止态交回，清单弃置；到期先到按已证主断言交回 not_found，清单按空放行；清单查询失败或被切断同样按空清单放行，不影响主断言。备用轮询只检查合法目标，不读取日志取得最后答案。
- 工具描述如实说明入口即查当前状态、静止目标按观察基准处理（首次确认或未报告翻转立即返回，已报告静止不重复交回、等待新变化）；不把「已结算仍驻留的目标读作运行」写成已知限制。

#### 3.2.5 无目标等待

无目标等待被任一可处理消息（2.2）或就绪内容唤醒：交付账本的内容就绪事件（作业结算、保活链释放）是本包内部唤醒通道，与消息唤醒进入同一竞速集合。唤醒后返回唤醒原因摘要与本批交付内容（2.6）；预算到期按到期口径返回并附就绪提示。就绪内容在无活等待时经完成消息交付（2.6），不要求模型发起等待领取。

#### 3.2.6 返回形状与模块组织

返回形状按结局枚举，全部分支可校验：

- 作业终态：`status` 为真实终态（`completed`／`killed`／`failed`）、`job_id` 与按 2.4 合并的输出。
- 子代理变化：`status='changed'`（可证新变化）或 `'settled'`（观察到停止）、`agent_id` 与变化说明——证据分级文案，不复制正文。
- 无目标消息唤醒：`status='message'` 与唤醒摘要（2.2 的摘要规则）。
- 插话 `status='interrupted'`；取消 `status='cancelled'`；到期有目标时 `status='running'` 附各目标已证状态，无目标时 `status='budget'`。有目标等待的全部出口（插话、取消、到期、任一目标事件）都附目标列表内其余目标的已证状态，不因单一目标事件丢弃其余目标的观察结果。
- 等待类出口统一附 `delivered`（本批交付条目：`job_id`、终态、字符数、截断标记）、`deferred`（延后条目标识）与 `waited_ms`；零等待的 `waited_ms` 为 0。提示文案按 2.5 分级。

模块组织：`lib/wait.js`（统一等待）承担入口、参数校验、预算武装、目标解析与竞速编排；两个目标适配模块是内部共享的基础模块——作业目标适配 `lib/wait-job-target.js`（作业三分、事件通道、终态读取）与子代理目标适配 `lib/wait-agent-target.js`（关系证据、注册表状态、双通道、观察基准与跨调用已报告状态登记）；消息部件、输出渲染与交付账本（`lib/delivery.js`）按 1.2 分工接续。旧两等待模块（wait-job、wait-agent）按第 9 章迁移清单退役，已并入统一等待。

工具定义声明并发安全（`isConcurrencySafe: () => true`，与现行五工具同款），`async_run` 与 `async_workflow` 的首次等待保持同款声明：宿主对未声明工具按排他串行执行，漏声明会使同拍并行等待静默退化为串行，2.6 的并行批次规则失去覆盖对象。声明进入第 9 章迁移清单对 `lib/wait.js` 的要求。

### 3.3 可续子代理

[派生模块](<../lib/agent.js>)经 `ctx.subagents.startActivation(spec)` 创建。目标调用形状如下：

```text
spec = { provider: 后端名, label: description,
         request: { prompt: text 内容块列表, parent: 调用主体,
                    [cwd], [agentPreset],
                    [agentOptions: { [provider], [model], [reasoningEffort] }] },
         signal: exec.signal, delivery: 'parent' }
activation = { childId, [messageId], result, dispose }
```

`SubagentActivationSpec.request` 的类型为 `Omit<SubagentStartRequest, 'label' | 'signal'>`。`label`、创建 signal 和 `delivery` 放在 spec 顶层，不放进 request。

**先决定是否触发支持预检。** 判据与目标 `@deepseek-ai/dsh-tool-subagent.requiresRoutePreflight` 同形：显式提供 `provider`、`model`、`reasoning_effort` 中任一项，或工具行 `agentOptions` 配置了 `provider`、`model`、`reasoningEffort` 中任一项。触发时，先合并后端 `agentRouteDefaults` 与行默认，再叠加显式参数。只有 `maxTokens` 等非路由键时不触发预检，后端路由默认也不参与。

**再决定创建请求是否携带 `agentOptions`。** 任一层贡献任一键就携带，包括显式路由／强度、行配置中的路由或非路由键，以及预检触发时折入的后端默认。例如行配置只有 `maxTokens`，请求也携带 `{maxTokens}`，但不因此预检。所有层都没有贡献时省略 `agentOptions`，宿主按父值继承，不额外应用后端路由默认。成功回执必须按实际有效值说明来源。

这里有两个不同的合并对象：支持预检使用的参数，以及最终交给 `startActivation` 的请求。预检返回值不回填请求；预检临时补入的推理强度不能直接被描述成最终子代理继承。最终行为按请求与宿主 `resolveChildAgentOptions` 核对，该函数只合并父值与请求覆盖，不自行并入后端路由默认。

静态核读依据为 dsh `0.2.1-rc.4` 的上述 `resolveChildAgentOptions`、`requestedAgentOptions` 和 `requiresRoutePreflight`。逐项验证按 8.2「子代理和路由」中的请求与回执核对执行。

**公共参数兼容**（需求 2.3.1）。`async_agent` 的公开参数与 dsh 原生子代理创建工具保持名称、类型、必填条件、缺省及校验语义一致：`description`、`prompt` 必填字符串；`cwd` 可选，指定子代理初始目录，缺省继承调用主体当前有效目录，相对路径以该目录解析，后续目录变化互不影响；`provider`、`model` 可选且必须成对，值为准确 LLM 路由 ID，省略时按 dsh 配置默认、后端路由默认及父路由继承顺序解析（后端路由默认的参与边界按 3.3 携带规则：仅在预检触发形态——显式请求路由或推理强度字段，或路由类配置默认——下折进携带值，无携带时不应用）；`reasoning_effort` 可选非空字符串，可单独指定并校验有效路由；换路由时的预检参数与最终继承分别按下文核对；`agent_preset` 仅在工具配置了可选预设且后端支持独立预设选择时暴露，按允许集合校验，不据此向原本无权选择的预设开放权限。可选预设集合与允许集合来自本包行配置根键——与宿主原生工具行同形的 `agentPreset`／`allowedAgentPresets`／`agentOptions`，与行身份字段同层、非 volatile、不进设置表单；本包两个预设的工具行不配置这些键，`agent_preset` 恒不暴露，验收只验不暴露与显式报错，自定义行可按原生同一语义配置（含 `allowedAgentPresets` 显式空数组的可读拒绝，5.1）。条件键的在场与缺省文案随 dsh 当前配置与后端能力取值（可选预设集合、后端 `agentRouteDefaults`、`capabilities.agentOptions`、`prepareContinuable`），与原生工具同一条件，不扩大也不缩小；静态依据为 dsh `0.2.1-rc.4` 的 `@deepseek-ai/dsh-tool-subagent` 公开参数定义及其条件分支。未知参数显式报错并列出当前支持键；dsh 原生工具的内部配置不是调用参数，不开放任意透传；宿主 request 允许 `outputSchema` 等其他可选字段，本工具不因此扩大公开参数。

**路由合并与支持预检**。先执行成对与非空校验，再按上面的触发和携带规则构造配置默认：工具行 `agentOptions` 覆盖后端 `agentRouteDefaults`，后端默认只在预检触发时参与。

叠加显式请求前，`requestedAgentOptions` 先判定是否换路由。比较基准的 `provider`／`model` 分别取配置默认，缺少的一侧取父值。如果请求显式提供 `provider`（已校验与 `model` 成对），且任一侧不同于该基准，同时没有显式 `reasoning_effort`，就先从配置覆盖中删除 `reasoningEffort`，再叠加请求的 `provider`／`model`。显式提供强度时以请求值覆盖；没有模型选择请求时原样返回配置默认。此删除发生在支持预检之前，改变实际携带的合并选项，不只是省略临时预检参数。实现依据为[派生模块](<../lib/agent.js>)的 `requestedAgentOptions`。有效路由缺少的一侧仍由父值补齐；最终父强度继承另按下面的宿主合并核对。

预检通过 `llm.resolveCallConfig` 检查有效路由和模型支持信息。构造这次预检的参数时，只有有效路由未变且后端没有路由默认，才用兼容的父推理强度补缺。换路由而未指定强度时，预检不使用旧路由的强度，模型默认的解析与校验由 LLM 运行时负责。

这不是最终子代理强度的保证。`resolveCallConfig` 的返回值未回填 `mergedOptions`，`startActivation` 仍接收原合并请求。最终强度须按实际请求及宿主 `resolveChildAgentOptions` 的合并结果核对，不能从预检省略强度推导最终不继承父值。预检通过后、启动前还要确认后端未变、调用未取消。

**模型选择策略实时读取**（需求 2.3.2）。策略唯一来源是 dsh 现有的子代理模型选择开关与允许名单：每次 execute 经公开 `subagentModelSelection` 服务 `current()` 现读当前生效值（volatile 设置，读即当前值），已有会话、新会话、恢复会话及各层子代理的后续派生同样生效，无需重开会话或重启实例。本包不注册宿主同键 `subagentModelSelectionPolicy` 投影，不以会话开始时写入的策略记录限制后续调用，也不修改 dsh 原生工具的策略；旧会话中原生工具仍按宿主采样链使用其会话内记录，本包不把它当作自己的实时配置。

- 开关关闭时显式 `provider`／`model`／`reasoning_effort` 被拒绝；全部省略按配置默认或继承路由解析，不因名单变化被拒。名单外路由拒绝且不派生。可更换路由解决的拒绝——名单外路由、预检拒绝（`llm.resolveCallConfig` 报模型或推理强度不受支持）与启动前确认名单已撤销所选路由——保留真实拒绝原因，并提示调用 `async_list_subagent_models` 列出或搜索；查询方式保留目标工具条件（`target_tool="async_agent"`），不指路其他创建工具。预检拒绝的宿主原文按 6.3 口径单行化并截断，完整原因进操作者日志；操作者日志行中的路由标识（provider／model，同为模型可控值）一样按 6.3 单行化（CR／LF／TAB 转义）——带换行的准确路由 ID 不得拆出第二条日志行，也不改变准确 ID 本身与校验语义。这类拒绝都发生在创建前：零派生、不返回 child id。提示文案取[两语表](<../lib/text.js>)的双语键。
- `current()` 抛错（含启用但名单为空、非法或重复路由）、设置服务缺席时，按真实原因可读拒绝显式选择，不用旧值、全部放行或任意模型替代；两者都不影响其他异步工具及无显式模型选择的派生。
- 一次调用内使用同一份读取快照完成合并与校验，紧接启动前重读确认显式选择仍开启、所选路由仍在当前名单内。失败诊断分三种，均拒绝本次调用、零派生、不返回 child id，也不使用过期许可：
  1. 重读本身抛错：说明策略读取失败，保留真实原错（按 6.3 单行化与截断），给出通过 `async_list_subagent_models`（`target_tool="async_agent"`）查询及稍后重试的出路；不据读取失败断言设置已变化或路由已撤销。
  2. 重读成功且开关已关闭：按显式选择已关闭口径，使用 `error.selectionDisabled`，提示省略显式路由与推理强度以采用配置默认或父继承。
  3. 重读成功、开关开启且所选路由确不在当前名单：按名单撤销口径，提示保留目标工具条件重新查询后再调用。
  读取失败与名单撤销使用不同词典键，中英文只陈述当次已证实的原因。查询结果（3.6）不是创建授权。
- 已运行子代理不自动换模型、不停止。

后端缺席、不支持 `startActivation`、后端没有 `prepareContinuable`、指定路由或推理强度而后端不支持 `agentOptions`、指定或配置了默认预设而后端不支持独立预设选择（无 `capabilities.agentPreset`，或后端 `inheritsParentContext` 不接受独立预设）、策略拒绝，都在派生前可读失败。保留可续后端要求，不能因宿主也能创建外部单次 activation 而扩大产品支持范围。创建阶段拒绝只报告实际错误，不返回虚构 child id；发布前的局部资源回收由宿主启动事务负责。

成功回执立即包含 `started`、`agent_id`（下文 child id 即此字段值）、实际生效路由及有界等待指引（需求 2.3.1）。核验回执时，比较实际子请求与目标宿主 `resolveChildAgentOptions` 的合并结果，不只比较提示字符串。

回执条目分别标注 provider 与 model 的值和来源：

| 实际来源 | 回执应写什么 |
| --- | --- |
| 显式请求 | 请求值及显式请求来源。 |
| 请求携带行配置默认 | 携带值及工具配置默认来源。 |
| 预检触发后，请求携带后端默认 | 携带值及后端默认来源；与行配置并存时以行配置覆盖。 |
| 请求缺少该侧路由，由宿主补父值 | 从与派生侧相同的数据源现读父路由，写继承值及父继承来源。读不到具体值时明确说明，不编造。 |

行配置仅给 provider 或仅给 model 时，会形成混合来源。两侧分别标注，不能把整条路由都写成继承。无任何贡献而省略 `agentOptions` 时，两侧实际均为父继承；宿主不会额外应用后端路由默认。

推理强度同样区分显式请求、工具配置默认、后端默认与有依据的父继承。父继承附注的判据是有效路由未变且后端无路由默认；无从判定时不编造，也不将预检补值当作最终继承证据。回执条目只写实际值与来源，不重述策略状态。

创建调用只 await 宿主接受启动，不 await `activation.result`，不注册等待计时器、轮询或作业。后台所有权约定为：

- 宿主 activation 管理器拥有已接受运行、后代所有权、自然结算、资源释放和父会话通知。`delivery:'parent'` 使最终结果经宿主通知交付；本包不转为 `caller` 后自行补发答案，也不重复发送结算通知。
- `spec.signal` 只控制发布前的创建。发布后，工具调用返回、该调用 signal 随后取消，以及任何有界等待的消息／取消／到期，都不取得停止 activation 的权限。本包不将等待信号接到后台运行，也不在工具出口、finally 或工具行卸载时调用 `dispose`。
- 返回对象取得后立即为 `result` 注册成功与拒绝处理，不延长启动回执。`result` 在宿主结算清理及通知处理后落定，但 resolve 不证明父主体已收到消息，也不证明清理没有失败；宿主可以保留已捕获结果并另行报告清理错误。`result` 只是观察通道：正常结算不在工具结果里重复交付答案；非正常 `stopReason` 不冒称成功；捕获等基础设施故障导致的拒绝经生命周期诊断出口报告，附准确 child id，不伪装成创建失败、成功结算或已通知父会话。处理回调本身及其派生 Promise 的拒绝也必须承接；诊断不依赖工具行仍在场，不建立无限期结果缓存。
- `dispose()` 是停止并释放这一次 activation 及所拥有后代的异步操作，不是「放下回执」。自然结算由宿主自动释放，本包不需要为了避免泄漏而立即调用它。显式停止仍走宿主管理入口；若后续正式设计确需直接调用 `dispose`，必须限定确切 activation、明确停止授权并 await 或承接释放失败，不能按 child id 缓存旧句柄去停止同 id 的后续恢复。

静态依据为 dsh `0.2.1-rc.4` 的 `@deepseek-ai/dsh-subagent` 中 `SubagentActivationSpec`、`SubagentActivation`、`startActivation`，以及管理器的 `startLocal`／`watchLocalSettlement`／`finishDisposal`／`receipt`。这些接口符号已按 dsh `0.2.1-rc.4` 安装树核实在场，自然释放路径的逐项核读按 dsh `0.2.1-rc.4` 重新核验（待验证）；立返时序、发布边界取消、拒绝诊断与实际父会话投递仍待验证。

[策略形状](<../lib/agent-policy.js>)的目标定位：派生路径不注册同键投影、不执行会话采样——不得以不同 fold、stateVersion 或 schema 重定义宿主 `subagentModelSelectionPolicy` 投影，也不得追加采样改变原生工具的会话策略。宿主策略定义的形状副本仅在 3.6 解读原生会话投影确需形状依据时保留为纯形状参考，不承担派生采样职责。现行[策略一致性检查](<../verify/check-agent-policy.mjs>)看守（看守＝以测试钉住判据的既定内部称谓，下文沿用）形状副本与宿主定义的同形，钉住「无投影注册、无采样」的现行事实。静态同形不代替实际指定路由验证，路由验证按第 8 章。

### 3.4 编排作业

[编排模块](<../lib/workflow.js>)读取组合内 `workflowEngine`，沿用需求 2.4.1 的脚本和钩子契约。注册成功后才 `engine.start`；解析／meta 错误原样作为创建错误，不被包装成并发拒绝。

作业 `kind='async-workflow'`、label 为 meta.name、description 进进度；cancel 调 run.cancel，等待 exec signal 不接运行取消。引擎 stopReason（completed／cancelled／error）分别映射为作业终态 completed／killed／failed，并在清理和日志摘除后保持可用结果。

完整命令回显开关对编排作业的受控回显物是 script 正文（需求 9.3.4 的「内嵌脚本」）：关闭时交付条目、完成消息与任务列表不含 script 正文，以作业编号、`description` 及状态呈现；开启时交付条目与完成消息的状态行可附 script 正文（受批次预算与裁剪约束）。注册名称恒为 `meta.name`，不随该开关取值，任务列表（`job_list` 渲染源）始终不含脚本（5.6）。

活动 mirror 订阅 phase、log、agent-start、agent-end 写 log 通道，phase 更新 progress。顶层 recorder 写 `tool-workflow/run-start`、`agent-start`、`agent-end`、`run-end`；append 失败停止该 run 的记录并告警。`exec.parent` 在场不写持久 recorder，mirror 和结果仍有效。

最终文本在闭包暂存，后台最终 result 由 2.4 合并消费。脚本引擎限制仍来自宿主部署，不能在描述中伪称固定并发数。`async_workflow` 的描述必须同时说明使用条件（用户明确要求的 workflow 或大规模多代理编排）与可用替代入口（一两个委托使用 `async_agent`），两语一致（需求 2.4；设计 5.6）。

编排首次等待的返回提示同受 2.5 证据分级：提前结束（插话、取消、预算到期；非目标通知不提前结束）后的完成优先复查读不到快照（`jobs.list` 抛错或清单查无）时，按未证实档给出句柄与复查出路，不断言编排仍在运行；共享模板对编排路径称「工作流／编排」，不误称「命令」，中英两档同受 5.6 约束。编排作业的进度日志汇总（阶段与子代理起讫）是可选内容，按 `workflowProgressLog` 开关筛选后进入交付（2.6）。

宿主 `PtcWorkflowEngine` 固定依赖 `subagents`、`ptcRuntime`、`sandboxPolicy`、`workingDirectory`。delegation 组继续仅隔离 `workflowEngine`；新增依赖必须在该组的引擎上下文中可解析，不能因为宿主根上有服务就宣称组合已满足。真实 cordis 接线须覆盖两个预设、宿主行和自定义挂载，不通过扩大隔离范围或绕过注入临时掩盖缺项。

自定义组合装载 `async_workflow` 行时，delegation 隔离组内必须同时包含编排引擎提供行（目标基线为 `@deepseek-ai/dsh-workflow-ptc`）——仅含工具行的组合属引擎缺席形态；工具指引与公开组合示例（用户参考五工具组合）按该组合要求说明。引擎缺席时，`async_workflow` 在注册作业前明确拒绝；引擎运行阶段无法取得有效目录或执行当前沙箱策略时，保留实际失败并按真实结果结算。目标引擎在运行时不支持沙箱、会话策略又不是 `danger-full-access` 时拒绝执行。本包不为让编排启动而清掉策略、自动升权或改用无沙箱引擎；首次等待结束也不停止引擎。隔离范围、缺服务和受限策略的反例均须验证。

宿主 PTC 编排引擎的核验基准：`maxConcurrentAgents=0` 时自动取 `min(16,max(1,availableParallelism()-2))`，`maxTotalAgents=1000`、`maxItemsPerCall=4096`、`syncTimeoutMs=5000` ms。这些是宿主引擎出厂配置，不是本包新增参数，部署可改。dsh `0.2.1-rc.4` 的 `@deepseek-ai/dsh-workflow-ptc` 中 `PtcWorkflowEngine` 注入、Config 和 start 的符号与配置键已按 dsh `0.2.1-rc.4` 安装树核实在场，逐项静态核读按 dsh `0.2.1-rc.4` 重新核验（待验证）；钩子契约、隔离组内装载及运行行为仍待核验。`@deepseek-ai/dsh-jobs-local@0.2.1-rc.4` 的 `DEFAULT_MAX_CONCURRENT_JOBS_PER_OWNER` 出厂值为 10，已按 dsh `0.2.1-rc.4` 安装树核实在场；触顶提示仍须反映宿主实际生效值。

### 3.5 两个预设的声明与隔离

[异步模式补丁](<../presets/dsh-async.patch.yml>)和[异步创造补丁](<../presets/dsh-async-create.patch.yml>)各声明一个预设。`config.plugins` 分别以 `@deepseek-ai/dsh-web-app` 随包 standard、cordis 预设为基线，不以插件当前行集合代替宿主基线。当前四个受支持宿主的随包基线相同（rc.2 与 rc.5 安装树的两个随包预设文件按 SHA-256 逐字节核对一致，rc.3、rc.4 按出处核读），仍按每个宿主安装件核对随包 standard 与 cordis 基线，某宿主改动基线时以该版本为准。

#### 3.5.1 保留基线功能、五工具与隐藏读取入口

两个预设禁止同步 shell 及原生单发／fork／workflow 创建入口。顶层提供 `async_run`、`async_wait`、`async_agent`、`async_list_subagent_models` 四行，delegation 组提供 `async_workflow` 行——五件本包工具各一行。保留编排引擎、非阻塞管理入口（宿主 `job_list`、`job_kill` 及作业控制器随行保留）、创作 skill 及基线其余工具，不把禁用行当作活工具。

原生 `job_output` 对模型隐藏（需求 9.3.5）：作业正文改由本包完成消息与等待返回直接交付（2.6），读取入口不再进入模型目录。

隐藏经宿主工具服务的公开作用域限制实现，不改宿主源码。挂点是 **`agent/created` 时对 Agent 作用域调用 `restrict`**（真机首测修正后的口径）：

- **为什么不在行装载期直接 restrict**：`tools.restrict` 的前置校验要求 `deny` 名位于调用方视图的**可限制名单**（继承面上的工具）。预设树内 `tool-jobs` 行注册的 `job_output` 与本包各行同属预设层——同层注册不进本层的继承面，行装载 ctx 上调用必然以「unknown global tool "job_output"」被拒，与行序无关（真机首测实证；曾按「tool-jobs 行先行装载即可」立论，不成立，行序对账判据保留但不再是隐藏的前提）。Agent 绑定预设后，预设层是它视图里的祖先层，`job_output` 成为可限制的继承项——这正是限制语义「过滤继承面、豁免自身层注册」的适用位置。
- **登记**：四个交付类工具行（`async_run`／`async_wait`／`async_agent`／`async_workflow`）在装载期经 dsh-scope 的祖先路由订阅 `agent/created`（监听器只收到加入本预设世代的 Agent，自建组合互不越界），在事件里对 `agent.ctx` 调用 `restrict({ deny: ['job_output'] })`——限制登记在该 Agent 自己的作用域层，只影响该 Agent 的继承视图，不触碰预设层注册本身，也不影响其他主体；限制句柄随行卸载回收，同模块实例内同一 Agent 只挂一次（跨模块实例的重复 restrict 按宿主「限制求交」语义幂等）。查询行（`async_list_subagent_models`）不挂（需求 9.3.5 末条「查询类工具不受影响」）。
- **降级承接**：`restrict` 调用失败（`agent.ctx` 缺席、服务不可用、前置校验不满足）按 try/catch 降级为 warn 日志，Agent 创建照常——隐藏失败只损失该 Agent 的隐藏效果，不影响工具可用性。
- **生效边界**：限制随**Agent 世代**登记——挂载任一本包交付类工具行的组合（本包两预设或自建组合）里创建的每个 Agent 都隐藏 `job_output`。这比「仅挂 `async_wait` 行才生效」更宽：交付类行都有直接交付语义（完成消息与首等直付），读取入口在任何一个交付行在场时都是冗余通道。预设外主体（未挂任何本包交付行的组合）不登记限制，`job_output` 照常可见；此时直接交付照常工作，宿主作业通知与原生读取并存不算重复投递（2.6）。

工具描述、纪律段、等待与延后提示均不引导调用隐藏入口，不重复领取已交付内容。

五工具默认仅挂本包两预设。使用者可分别挂查询或创建工具，自建组合由使用者决定，本包不改写其预设，也不改变 `async_workflow.agent()` 或其他引擎的策略、参数（需求 3.2）。自建组合挂载任一交付类行即按上节生效边界隐藏 `job_output`；仅挂查询行的组合不改变其原有工具集合。

维护补丁时先核对以下基线内容：

- `time-context`、`tool-schedule` 等行的顺序、配置、禁用条件保持，不改变市场或调度权限。
- `tool-plugin-manager`、`tool-plugin-market` 的禁用值逐字保持：standard 两行都是布尔 `disabled: true`；cordis 两行都是 `!!js "!ctx.get('profileContext')"`。因此创造上下文有 `profileContext` 时，异步创造预设保留插件管理和市场入口（需求 3.1、7.3.2）。
- persona prefix 原样保留 `You are a coding agent powered by the {{model}} model.`，不增改宿主身份句，也不把本包纪律塞入其中。不设置含 `{{cwd}}` 的 suffix；当前目录由 `working-directory:current` 上下文提供。
- 计划模式说明按目标基线整段同步，再核对与本包入口纪律没有冲突。不补造目标基线不存在的行和键；原生创建行禁用只控制入口，不用不存在的键表达后台行为。
- delegation 只隔离 `workflowEngine`，引擎行保持 `provider: spawn`。按 3.4 核对组内依赖；standard／cordis 没有 `working_directory` 直接工具行，本次不新增，也不以工具行在场代替目录服务验证。

#### 3.5.2 注册纪律段并确定顺序

本包常驻执行纪律由宿主角色注册为系统提示 section，运行时注入，不写进 persona。宿主 `dsh-system-prompt.section()` 支持函数文本：每次 `assemble` 调用函数，渲染时过滤空串段。

section 位于系统提示正文；context 只进入「Current runtime context.」快照消息。静默失败防护的现有 context 注册（宿主角色经 `ctx.inject(['systemPrompt'], …)`，见 6.2）是函数求值的同型先例，但不能用 context 代替这里的正文 section。

排序取宿主 persona 档之后的首档：persona 为 0，本包纪律为 500，与 `plan:policy` 同档。`comparePromptSections` 在同档按段名作次级键稳定排序，因此保持与 persona 的毗邻关系。段名使用本包命名空间，不改宿主段名或排序规则。

#### 3.5.3 每次求值、预设过滤和失败退场

纪律文本使用函数，每次组稿执行以下判断：

1. 读取当前配置快照的 `agentLang`，选择 en／zh，两语语义和约束相同，默认英文（需求 5.3）。
2. 根据组稿目标 Agent，使用 `ctx.get('sessions')` 与 `ctx.get('sessionProjections')` 读取会话 `agentPreset` 投影。这是与提问接管相同的同步路径。
3. 仅实际预设为本包两个预设时生成对应变体；其他预设返回空串。

无 Agent、服务或配置快照缺席、读取失败时，返回空串，纪律段不显示。不以无法确认的预设身份向其他会话注入纪律。

#### 3.5.4 两语文案、变体和开关

文案集中在[两语表](<../lib/text.js>)。en 档保留身份句之后的纪律原文，不重写；zh 档为等义译文，锚句表达同样约束。每语均有两个预设变体：

- `dsh-async`：包含不得传 `run_in_background: false` 的禁句。
- `dsh-async-create`：包含宿主 `subagent`／`subagent_fork` 已禁用、不要调用的说明。

常驻纪律不受 `silentFailureGuard` 控制；该开关只控制 6.2 的静默失败防护纪律段。两段分别过滤，不能混作同一开关。

常驻纪律包含三组要求：

| 主题 | 必须表达的约束 |
| --- | --- |
| 异步等待与直接交付 | 首次等待让出后按作业编号跟进度，作业结果经完成消息或 `async_wait` 直接进入上下文，不需要专门的领取调用；需要主动等待时用 `async_wait`（可带 `targets` 与 `wait_ms`，0 为立即检查），使用有界等待，不循环轮询，不为查进度重复委托 |
| 委托 | 一律后台，`async_agent` 是唯一入口；需要子代理的变化通知（含结算通知）时用 `async_wait` 指定 `agent` 目标；最终回答另以消息到达 |
| 提问角色（ASK-01 目标） | 提问和选项不使用人称代词；执行者、授权者、归属对象使用明确且可区分的角色名称；选项写清角色与动作，选择后角色指向一致 |

ASK-01 对应需求 9.1；其实施状态见第 9 章。

#### 3.5.5 修改后怎样验证

[预设校验器](<../tools/validate-preset.mjs>)按两个预设分别比较顶层／嵌套行集合、顺序、禁止行、五工具各一及组内位置、禁用状态和 persona：

- persona prefix 必须与基线身份句逐字一致，增改即失败。纪律不靠 persona 校验，而核对两语表 en／zh × 两变体，共四份。
- 每份核对后台委托、唯一入口、直接交付、有界等待、不循环轮询及各自变体差异句。任一必要锚句缺失即失败。
- 工具行核对五件本包工具各一行：顶层 `async_run`、`async_wait`、`async_agent`、`async_list_subagent_models`，组内 `async_workflow`；退役的两等待行名不得再出现。
- 隐藏核对待接线层完成：本包预设主体的模型工具目录不含 `job_output`，且 `job_list`、`job_kill` 仍在；其他预设主体不受影响（8.2 预设隔离行）。
- ASK-01 分别核对禁用人称代词、明确角色、角色加动作、指向一致四组等义锚句。
- 管理／市场两行逐字比较：`dsh-async` 布尔禁用，`dsh-async-create` 保留 `profileContext` 表达式。改布尔或表达式都失败。

校验器目标形态为五工具加隐藏登记，但校验器与替身仍须按目标基线重核。目标随包 standard／cordis 文件已确认在场，逐字核读待完成；文件在场或核读完成都不等于补丁已重建、真机已加载。版本依据取需求 7.3，不写机器路径。

运行验证按 8.2 核对每次求值、语言更新、实际预设过滤、失败空串、两变体和独立开关；其他宿主预设以反向对照确认工具及提示不变。算法检查不能代替真实接线和组稿证据。

### 3.6 路由查询

`async_list_subagent_models` 是独立只读工具，实现位于[路由查询模块](<../lib/list-models.js>)。它列出或搜索当前会话可见的子代理 LLM 供应商／模型，并说明对目标创建工具的适用性。它不创建代理、不推理、不修改配置或当前 Agent 路由，与原生 `list_subagent_models` 可以同时挂载。

查询工具单独挂载也能查目录，不读取其他工具行、宿主行或派生模块的内部闭包。策略与目录经宿主公开服务取得。目录访问委托 `llm`，适配器访问遵循 dsh；本包不自行请求网络或访问凭据（需求 6.2）。`llm` 缺席时按 1.3 返回可读错误，不创建代理或伪造条目。

#### 3.6.1 选择查询参数

| 参数 | 条件与行为 |
| --- | --- |
| `provider` | 可选，指定准确供应商 ID |
| `model` | 可选；提供时必须同时提供 `provider`，查询准确模型详情 |
| `query` | 可选，去首尾空白；全空白视为未提供。非空搜索与准确模型详情冲突时可读拒绝 |
| `target_tool` | 可选，指定当前会话可见的创建工具名，含用户配置名 |
| `page` | 正整数，默认 1；大于 1 必须携带 `version` |
| `page_size` | 整数，默认 20，范围 1—100；非法值可读拒绝 |
| `version` | 首轮可省略，续页绑定原查询与结果版本 |

#### 3.6.2 构建目录与读取详情

目录来自 `llm.listProviders`、`listModels`、`resolveModelInfo`。供应商、模型的准确 ID 和原始元数据保持原样；同名但 ID 或供应商不同的条目不合并。结果文案按 `agentLang` 提供完整中英文，不返回凭据、密钥或私有接口地址。

准确详情返回模型名称及推理强度的 ID、名称、默认项。元数据缺席就说明缺席，不编造强度或替 Agent 选择。目录可见只说明已取得信息，不证明策略许可、凭据有效或远端可用。

**解析失败按稳定 code 分类，不解析 message 猜原因。** dsh `0.2.1-rc.4` 的 `@deepseek-ai/dsh-llm` 通过 `HarnessError`／`LlmError` 携带公开 code：

- `UNKNOWN_MODEL` 及同类表示不支持的 `UNSUPPORTED_*`：报告「不支持」。
- 其他 code，包括网络失败和 `INVALID_MODEL_INFO`：报告「读取失败」，保留原始原因。
- 没有稳定 code：仍报告「读取失败」，不编造定性（需求 5.7）。

这些失败都不同于「目录未列出」，也不能被报成有效可用。部分供应商失败时，标记失败与结果不完整；匹配总数只计算已取得的结果，不把失败部分记为零模型。

**将允许但未列出的路由并入候选集。** 只有通过下文目标证据链取得已确认允许集合后，才按准确 ID 并入所属供应商的浏览与搜索结果。条目标注来源为允许名单；缺少名称或元数据时不写对应键。供应商本身未列目录时，同样建立来源明确的条目。准确详情能由 `resolveModelInfo` 解析则返回详情，不能解析则按上面的失败类别报告。

合并顺序为：目录条目与名单派生条目全部进入候选集→统一搜索→分页。正常目录条目继续列举，不被名单并入逻辑替代。未列供应商的供应商内搜索也逐条匹配 `query`；没有匹配时返回空页、总数零，不生成本页示例。

#### 3.6.3 搜索供应商与模型

跨供应商搜索和指定供应商内搜索共用规则：去首尾空白、忽略大小写、按 ID 或显示名称作包含匹配，不默认使用正则。未列条目没有显示名称时，只按模型 ID 和供应商命中判断。

供应商 ID 或显示名称命中时，其模型整组随行：跨供应商搜索同时列出供应商条目；供应商内搜索列出该供应商全部模型。未列供应商只按准确供应商 ID 判断，命中后全部允许名单路由随行。指定 `provider` 不取消供应商字段匹配，因此两种搜索方式在同一供应商下的命中模型集合一致。

#### 3.6.4 找到目标创建工具

`target_tool` 只影响筛选、适用性和调用指引，不授予权限。当前核读尚未确认公开的按工具查询策略方法；这不等于断言不存在，目标判定须依据下列公开证据。

先经宿主工具投影按调用方作用域枚举可见工具（同 6.2）。同时声明字符串 `description` 和 `prompt` 的模型侧 schema 是创建候选，再排除本包查询与等待工具——排除集合在[路由查询模块](<../lib/list-models.js>)以固定工具名清单维护（`SHAPE_EXCLUDE`），五工具改写时同步替换该集合（见第 9 章迁移清单）。名称和形状只能产生候选，不能证明注册来源或策略归属。

- 省略目标且只有一个可识别候选：采用该工具。
- 多个候选、没有候选或无法可靠识别：报告「适用性未确认」。单独挂查询工具仍可查目录，但不宣称已有可用创建入口。
- 具名目标不存在、不可见或不能识别为创建工具：报告「不允许选择」及原因。目录按已获依据继续返回，不终止查询，也不生成适用创建示例。

#### 3.6.5 判断本包创建工具

面向 `async_agent` 依次核对身份、实时策略、创建后端。三段齐备才判「允许选择」，其中的身份状态也进入版本令牌。

**身份：确认工具对象，不凭名称确认。** 经 `tools.get(name, scope)` 取得实际可见定义，与[工具行登记簿](<../lib/tool-rows.js>)按对象同一性比较。登记簿是模块级 WeakMap，键为工具对象，值为该行配置视图；入口每行 `ctx.tools.register(tool)` 成功后登记，卸载后对象不可达即可回收，无须单独清理。

- 命中：确认是本包创建行，并取得创建行配置。
- 可见定义来自外来登记或被同名行遮蔽（含原生行配置 `toolName:'async_agent'`）：未确认，basis 为 `list.basis.asyncForeignName`。
- `get` 缺席、抛错，或候选已枚举而 `get` 查无：未确认，basis 为 `list.basis.asyncIdentityUnreadable`。
- 查询行与创建行不在同一模块实例（如重复安装），登记簿查不到：未确认。

未确认时给原因，不读策略和后端、不生成示例，不用本包默认或查询行配置冒充创建行配置。两个 basis 键按 `list.basis.*` 约定提供同义双语。静态依据是目标 `@deepseek-ai/dsh-tools.get(name, scope)` 返回实际定义对象，以及 `@deepseek-ai/dsh-scope` 按引用保存（「Values are borrowed」）；对象同一性是宿主惯用判别。

**策略：读取创建侧同一来源。** 现读 `subagentModelSelection`。服务缺席或读取失败为未确认；开关关闭是已确认限制，判「不允许选择」（同 3.3）。

**后端：使用创建行配置。** 按该行的 `subagentProvider` 调用 `subagents.getProvider`。下列任一条件成立，都按后端限制判「不允许选择」，不给适用示例：

- 后端未注册。
- 未声明 `capabilities.agentOptions`。
- 未提供可续支持 `prepareContinuable`。
- 创建行配置了默认 `agentPreset`，但后端无 `capabilities.agentPreset` 或 `inheritsParentContext`，不能独立选择预设。

最后一项与宿主 `SubagentPresetSelection.assertProvider` 同判。注册表读取抛错则为未确认。查询和创建须共用相同后端前提及创建行配置；同一稳定组合出现「查询允许、创建拒绝」即不合格。

#### 3.6.6 判断原生创建工具

原生目标依次核对身份、参数、会话策略。三段齐备才判「允许选择」，逐路由按该会话投影判断。自定义工具名同样核对，不凭名字默认确认。

**身份需要两条公开依据同时成立。** 工具定义不带来源标记，`get`／`view` 只返回定义；作用域自有层还可遮蔽继承层同名工具，且原生行本身可配置 `toolName`。因此名称加参数形状不足以确认来源。

1. 所在会话的 `subagentModelSelectionPolicy` 投影在场，证明原生插件在该会话组合中活跃（该投影由原生插件注册、写入）。
2. 调用方作用域组稿中的 `tool:<目标名>` 段非空。原生插件只在 `tools.get(tool.name, scope) === tool` 时渲染该段，证明当前可见对象就是其注册对象。段缺席或为空意味着未装载、别名不对应或同名遮蔽。

第二条经 `systemPrompt.assemble` 现读。公开接口无按作用域单读一段的通道，因此每次目标判定最多组稿一次，不跨调用缓存；服务缺席或组稿抛错按读取失败报告未确认。任一依据不足也报未确认，给缺失段与原因，不生成适用示例，不能以形状加投影取代双依据。

残余信任边界：其他插件可通过同键投影或同名组稿段仿冒上述依据，公开接口不能判别。查询结论不授予权限，实际调用仍由目标与宿主校验。静态依据为目标 `0.2.1-rc.4` 的 `@deepseek-ai/dsh-tool-subagent` 段渲染、投影注册写入，以及 `@deepseek-ai/dsh-system-prompt` 的公开接口；未做真机验证前只按静态核读处理，功能核对见 8.2。

**参数：** 可见 schema 必须含 `provider`／`model`。原生行 `modelSelectionSettings` 决定是否暴露，形状也是启用证据；缺少则判「不允许选择」，说明目标不接受显式路由。

**策略：** 读取会话投影 `subagentModelSelectionPolicy`（事件类型 `subagent/model-selection-policy`）。读取失败为未确认；状态为空说明该会话未启用原生选择，判「不允许选择」；非空时使用其中路由表。不把参数开关关闭、但其他来源留下策略的目标误报为可选。

原生旧会话策略不是实时全局配置。全局新增路由可能仅对本包即时可用；反过来，全局撤销的路由也可能仍在原生旧会话名单内。两个方向都分别报告，不能按任一侧过滤另一侧。

#### 3.6.7 生成适用结论、计数与调用示例

目标结论与目录完整性分别报告，结果写明目标和依据：

| 条件 | 结论与计数 |
| --- | --- |
| 目标证据齐备并允许选择 | 供应商允许数按已确认集合计，含目录未列路由及仅在名单中的供应商 |
| 已确认目标不存在／不可见／不可识别、无路由参数或后端不支持 | 「不允许选择」，给具体限制；计数只报目录已知数 |
| 身份或策略归属不明，工具投影／会话投影／注册表读取失败 | 「适用性未确认」，给原因及重查出路；只报目录已知数，不出现允许计数 |

后端不支持包含 3.6.5 的全部前提失败，原生投影为空也属于已确认限制。不修改原生工具，不猜测缺失证据。

目标级允许时，逐模型按已确认名单标可选或不可选；名单外条目不能宣传为可创建。目标级不允许或未确认时，只报目录事实，不标条目可选性。准确详情按具体路由取档：目标允许但该路由不在名单，仍返回完整详情，结论为「不允许选择」，说明未获准。

调用示例必须同时满足目标允许、示例路由获准。浏览或搜索取本页第一条可选模型；本页无可选项则无示例。字段仅取目标实际可见 schema：声明 `provider`／`model` 才提供；`reasoning_effort` 还须模型支持。即使名称是 `async_agent`，也不能绕过形状核对。搜索、分页、目标参数和本包返回字段不得混入创建参数；原生示例不宣传为适用 `async_workflow.agent()` 或其他工作流。

查询不是后续创建许可。配置或目录变化后，创建仍执行目标自身校验；拒绝时保留目标条件重新查询，不换创建工具绕过限制。

#### 3.6.8 分页、令牌与续查

供应商、模型和搜索结果都先筛选后分页。同版本内按供应商 ID、模型 ID 字典序稳定排序，不重不漏。

版本令牌是不透明摘要，服务端输入必须覆盖所有会影响本次结果的内容：

- 规范化的 `query`、`provider`、`model`、`target_tool`、`page_size`。
- 当前可见目标身份及其判定状态。
- 全部相关策略内容（实时设置或会话投影）。
- 目录全部影响返回的字段，包括 ID、显示名称、条目说明 `description`，以及完整性标记。

只摘要 ID 不够。显示名会改变搜索，说明会改变正文；仅说明变化也须令牌失效（需求 2.3.4）。名单派生条目由已计入的策略决定，不额外新增输入。

摘要载荷有版本号。包升级改变摘要输入集时递增，版本不一致即不兼容；宿主升级本身不改本包载荷版本号，宿主内容变化按普通内容失效处理。两种失效都用 `error.list.versionStale` 拒绝续页拼接，指引重查，不为旧令牌另开兼容出口。

每页返回令牌、条目、匹配数、是否有下一页、续查参数，并回显目标及筛选。部分失败时总数为取得数，明确不完整。`page>1` 未带令牌可读拒绝；改变条件从新查询开始；失效从第一页重查，不混合新旧页。

`next` 包含下一页 `page`、`page_size`、`version`，以及在场的 `provider`、`query`、`target_tool`。可直接用于下次调用，稳定目录下应能依次翻完。正文页脚与结构化续查字段同源。越过末页返回空页、总数与重查出路，不报错或悄悄返回首页。

#### 3.6.9 呈现条目与空结果

先显示来源说明，再逐条渲染本页条目。未列供应商的来源说明不与条目互斥；同页第二条及以后的准确 ID、来源、可选性标记也必须进入正文。不能以结构化 `entries` 代替正文。

条目为零才显示空态，并区分条件：

- 供应商读取失败：显示读取失败、完整性及失败清单，不说「没有已列模型」，不把失败折算为零。
- 成功列举但零命中：显示空目录或无匹配。
- 未列供应商：由专属说明表达确无已列模型，或有路由但无匹配，不叠加通用空态。

未列供应商的三态沿用现有词典键，键文案不变：`render.list.unlistedProviderAllowed`（有条目时来源说明）、`unlistedProviderNoMatch`（有路由无匹配）、`unlistedProvider`（确无已列模型）。准确 ID、适用性、完整性与继续查询信息均不可被正文截断取代。

## 4. 提问接管、延长与迟到作答

### 4.1 接管和批次状态机

宿主角色在 `user-questions/request` 的前置 waterfall 应答者中执行同步保守判定。开关、根主体、实际预设、非计划评审全满足才接管，否则 `next()` 原生处理；预设读取失败不接管。

批次记录核心字段含 `batchId`、`sessionId`、`agent`、`lang`、`request`、`questions`、`receivedAt`、`expiresAt`、`phase`、`settled`、`signalRef` 与 `onAbort`（期间取消的载体）、`cancelTimer`（到期定时器的载体）、`next`（原生流程的可逆交还），以及落定用的 `resolve`／`reject`——枚举非穷举。phase 只有 `open`／`expired` 两值；全部作答或中止以独立 `settled` 布尔护栏防重复结算，批次随即出列。questions 保留每题 `open`／`answered`／`ignored`。

- take 取得请求进入时生效的 `askTimeoutMs` 作为当次初始窗口、建立一个 Promise 和计时器；入口与期间取消按 `ASK_ABORTED` 拒绝并清理。
- 全部作答／忽略整批次 resolve 原形 answers；计时到期保留已答，对 `open` 题给 `{id, selected:[], custom:<超时事实>}`，不是代答。
- 同步结算检查防止全部作答、取消、到期重复 resolve。expired 原调用已经结束，只留未答题供迟到提交。作答与忽略提交入口按服务端时钟同步比较 `now` 与 `expiresAt`：真实期限已过时，无论到期回调是否已运行，都不按窗口内结算，改走迟到路径并返回 `late`，原调用不因此复活。
- 迟到题在新批次接管时清扫超龄记录，`EXPIRED_TTL_MS` 按需求 4.4 的保留期定义；这不改变在窗提问期限。24 小时是到期记录在新批接管时的惰性清扫阈值，不是定时删除或迟到作答的硬性截止。无新批接管时，记录可以存活更久并仍可迟到作答。面向用户的帮助与超时合成答案的模型可见文案（`ask.timeoutCustom`）都须表达这一清扫时机——清扫是惰性的，只清已超时超过保留期的记录——不写成固定的「到期后保留／送达窗口 24 小时」，也不暗示到点定时删除或一律拒收；未送达时，直接出路是到题目所属会话直接回复。
- 卸载时先停自己的观察、计时和登记，对未结批次调用可用原生 next 并接管其返回的 Promise；原生不可用时明确取消。expired 不重复交还。

### 4.2 延长动作

配置字段 `askExtendMs` 落在提问接管参数组，默认值和范围引用需求 5.2；进正数断言、毫秒与秒两种读数、宿主／客户端两侧的字段界表（字段界表＝按需求 5.2 逐字段范围建立的宿主 schema 与客户端 parse 两侧界值表，下文沿用简称），不参与跨字段链。

远端方法 `extend(submission)`，载荷为 `{sessionId}`，只作用点击当时该组 `phase === 'open'` 且 `now < expiresAt` 的批次；追加时长取点击时生效快照的 `askExtendMs`。

- 新期限为原 `expiresAt + askExtendMs`；不重置题状态或原 Promise，不创建会话级继承标记，也不改 `receivedAt`。
- 每批次撤旧定时器，写新期限，再按剩余时间重挂。所有到期回调走同一个入口：先按服务端时钟比较 `now` 与 `expiresAt`，未到真实期限就重挂下一段，已到期才放行——排队中的旧回调不能提前结束，已到期批次不因回调稍晚而复活。
- 若剩余延时超过 Node 单次定时器可表达值（`2^31-1` ms），按该上限分段武装并在回调重查实际期限，不因计时器溢出变成 1 ms，也不据此限制用户已追加的期限。接管时的初始计时与延长后的重挂共用这一武装函数。
- 新批次从自己的初始窗口开始，不继承之前的延长。
- 返回 `{extended: n}`，n 为本次作用的在窗批次数；无在窗批次返回 `{extended: 0}`，同样是成功动作，不产生未来批次的状态。异常显示失败，不能假加时。

### 4.3 RPC、界面与语言

服务键 `asyncToolsAsk`，namespace `async-tools-ask`，使用公开 `TypertRemoteService` 与 `Remote` 标记。方法为 state、answer、ignore、extend，逐一登记进服务侧标记与客户端 strict descriptor 表；参数名 `submission` 与 descriptor 的 wire 名一致，裸载荷不另包一层。

state 返回 serverNow、按题展平 items 和待显示失败项。item 含 batchId、sessionId、questionId、题干、选项、multiSelect、receivedAt、expiresAt、phase；同批次重复期限供展示，不存一份客户端独立计时事实。answer／ignore 返回 delivered、late、gone 或 failed；extend 返回 `{extended: n}`。outcome 枚举不变，gone 分两口径：题已在他处落定返回普通 `{outcome:'gone'}`，界面交轮询收敛；批次或题记录缺席（清扫、结清出列或交还）返回 `{outcome:'gone', undelivered:true}`，客户端以可消除报错名单显示未送达（与迟到投递失败名单同一方式，需求 4.4）；忽略提交命中缺席批次同判。failed 表示本次没有送达。非法作答不产生新返回值：answer 在记录与分发之前按原题校验，拒绝经 RPC 错误回执返回（本节作答校验，客户端按明确拒绝档显示）。

客户端对 gone 与 failed 给可见说明，不以成功提示清掉未送达事实。

**客户端怎样解释动作结果。** RPC 动作在客户端的表述分三类：明确成功（服务端回执）、明确拒绝（服务端可达的失败回执）、未收到确认（请求已发出但无响应——超时、连接中断或响应丢失）。未收到确认不得断言动作未执行：提交不说「答案未送达」，延长不说「未生效」；不确定结果以既有 state 轮询与丢失名单收敛，不为此建通用网络恢复系统。

浏览器轮询 state 的设计间隔为 1000 ms，页面恢复可见及每次提交后立即刷新；后台页节流不当作服务端停止计时。overlay 挂 `shell.overlay` 全帧浮层槽（条目自定位右下），sidebar 挂 `sidebar.footer.action` 槽，复用 AskList 与 AskItem。徽标计数为未处理问题数，全部处理后消隐；徽标与组头入口跳转所属会话。每个会话组的组头提供「增加等待时间」按钮，与既有组头动作并列；点击只发本组 sessionId，成功后立即补一次 state 轮询，新期限经 serverNow 校准显示，题 key 保持 batchId/questionId，期限刷新不丢本地答案草稿。extend 未收到确认时提示只说明结果未知、以面板状态为准：延长每次成功都会累加（4.2），重试前先等 state 读回真实期限，期限已延长不再补点，未延长才重试，不把重复累加改成伪幂等。明确拒绝走面板顶报错通道，可重试，不假报加时成功。按钮文案 `ask.extend` 两语对应。

为防止旧响应覆盖新状态，state 读取采用**读取代际**：每次读取都绑定生命周期代数和单调递增的读取序号。

state 请求的五个入口都遵守这一规则：定时轮询、页面恢复可见、作答或忽略成功后的补查、延长成功／明确拒绝／未收到确认后的补查，以及开启或重新开启后的首查。动作后的补查没有额外优先权，就是普通 state 读取。

1. 接管关闭、重新开启或客户端贡献卸载时，推进生命周期代数。关闭时同时清除定时器、题目及 serverNow。
2. 收到回执时，先确认代数仍是当前代，再确认序号大于已应用的最高序号。两项都满足才应用，成功与失败回执同判。
3. 丢弃旧代或同代较旧的乱序回执，不写 items、serverNow、期限与剩余时间，不设置 `callFailed:'state'`，也不触发界面通知。已取得的新题目、徽标计数和期限不能被旧响应回退。

此机制只控制状态响应的应用顺序，不改变作答、忽略、延长、迟到投递或丢失名单的动作语义。

座位（`askUiSeat`，即字段表中的「待答问题显示方式」）的默认值与选项：默认值为 `sidebar`（需求 5.2）。默认值只在宿主配置行与用户层都未显式设置该字段时生效；已有合法显式选择（`overlay` 或 `sidebar`）保持原值、不被清洗，保存路径只提交改动字段（需求 5.1）。未显式设置该字段的用户在接管开启时看到侧边栏底栏徽标，显式选择任一座位的用户界面不变。显示方式不决定是否接管，`askTakeover` 默认关（需求 4.1）。客户端 `readConfig` 带防御回退：快照值层整体缺席时，回退值与默认值同为 `sidebar`。选项渲染顺序 `[sidebar, overlay]`，与需求 5.5 的选项命名顺序一致；选项文案的默认标记挂在「侧边栏底栏徽标」，与需求 5.2 一致，标记不指示用户当前选择（词典键位见设计 5.6）。

倒计时用 serverNow 校准展示，服务端期限为权威；超时显示可补答。失败项即使待答数为零仍可见，明确送达失败，阅读确认后才消隐。

AskItem 以 batchId/questionId 关联题目，分别维护预设选择、自定义项选中状态与文本草稿，两种面板共用。选择关系和初始状态按需求 4.2.1；无预设项同样维护独立自定义项，不以文本内容或焦点推断选择。

- 预设项与自定义项共用选择逻辑：单选互斥，多选分别切换。点击自定义输入框或主动输入非空白文本时选中自定义项，按题型处理其他项；多选已选预设项保留。不分析文本与预设项是否语义冲突。
- 通过选择控件取消自定义选择，或切换单选项时，可保留文本草稿，未选中草稿不提交；再次点击输入框或主动输入有效文本时重新选中。清空已选自定义文本保留其选中状态，不恢复旧预设项。仅键盘焦点移动、草稿恢复与 state 刷新不改变选择。
- 选中样式由选择状态驱动：预设项和自定义项统一使用醒目的整项底纹、单选或勾选标记及辅助边框。悬停与焦点样式独立，输入焦点不写入选择状态；长内容布局保留标记空间。控件向辅助技术提供题目、选项名称、单选／多选关系、选中状态及输入关联，支持鼠标、触屏和键盘操作。主题色映射只用主题定义中的别名 token，由[别名 token 检查](<../tools/check-alias-tokens.mjs>)静态把关；实际视觉效果按 8.2 真机验证。
- 有效性从当前选择和文本草稿计算：没有选中项，或选中的自定义文本去除首尾空白后为空，都禁用提交并就近说明原因；多选已有预设项也不能掩盖无效自定义项。按钮与快捷键共用此判定；空白检查不改写用户文本。ignore 独立，不转成空答案。
- answer 载荷从当前有效选择生成：既有 selected 表达已选预设项，custom 只在自定义项被选中且有效时承载原文，作为独立答案而非附注；未选中草稿不进载荷。服务端在记录已答或分发到窗口内／迟到路径前，按原题校验选择关系与有效性（[提问接管](<../lib/ask-takeover.js>) 的 `validateAnswer`，窗口内与迟到路径同判）：未知选项、单选多项、空白自定义、单选预设与自定义并存、未作答一律拒绝，拒绝不记已答、不投递；题已在他处落定按 gone 返回，批次或题记录缺席按 gone 附 `undelivered:true` 区分（`validateAnswer` 的 `gone`／`missing` 两态），均不以内容拒绝。拒绝原因文案两语随 `agentLang` 活读，读取失败回退 en。界面提交记录、工具返回与迟到通知共用已校验答案，题目信息与实际答案分开。答案记录沿用宿主提问协议的答案形状（`id`、`selected`、`custom`），不新增答案字段。

展示词典由 uiLang 选择；auto 订阅宿主当前 locale，不写全局语言。所有按钮和错误有两语对应。

### 4.4 迟到通知与轮次边缘

迟到作答构造 `source.kind='async-tools-late-answer'`、form notice、summary，正文自含完整题目与答案：稳定题号、题干全文、选项全集（含各选项自身的 description）、多选属性、4.3 已校验的实际答案或明确忽略状态与时间信息。题目信息与实际答案分开；自定义项选中且有效时与已选预设项并列为答案，不作附加说明，未选中的草稿不进入正文或摘要。summary 与正文表达同一组实际答案，与界面提交记录和窗口内工具返回一致。选项标签相同或相近时以 description 区分真实差别，不依赖模型记忆旧工具调用。不写成 source user。

空闲且无本包待启动投递时 followup，其他情况 inject 到 `nextStep`（待启动投递登记的语义见 2.6——已构造、尚未发出的投递项）；本包待领登记（已投出、待主体领取的本包消息清单，方向与待启动投递登记相反）与宿主 inbox 对账，不自建会吞消息的串行队列。最后领取点后的已接受消息由空闲观察补最小提醒，不重复答案正文。催领提醒使用本包自有 `form` 标记 `'reminder'`：宿主 `ContextForm` 枚举外值按不透明内容处理，不在 2.2 唤醒判定集合内；这是有意的本包命名空间选择，不用 `notice`／`relay` 等枚举值制造无效唤醒。

投递次序先于唤醒判定：构造通知后先经宿主通道投递（按上段规则选 followup 或 inject），投递被宿主接受（调用正常返回）之后才发布迟到作答事件、登记待领登记并武装空闲观察。投递抛错时不制造到达事实：不发唤醒事件、不写待领登记、不武装观察，RPC 回执 `failed`、审计记录与状态显示一致（4.3——failed 表示本次没有送达，界面不以成功提示清掉未送达事实）；等待中的 `async_wait`（无目标与有目标——迟到作答专门分支对有目标等待同样唤醒，按 message 出口交回并附其余目标已证状态，口径见 2.2 专门分支段）可被迟到作答唤醒并交回唤醒摘要；首次等待不被迟到分支打断，按原预算继续，到期照常交回，正文在领取点进入上下文（2.5）。先到答案也可入口命中——入口扫描读宿主收件箱，天然只命中已投递成功的消息，与事件口径一致；不要求把答案改成用户插话。补醒（`reminder`）失败转 lost 名单的既有路径不变；发送或补醒失败可见，不能用正常回执掩盖本包失败。

## 5. 配置快照、语言与设置表单

### 5.1 生效数据流

schema 默认值和范围只引用需求 5.2。[配置模块](<../lib/config.js>)持有单一 Config，根为普通对象。维护 schema 时，先按写入权限分清三类成员：

| 成员 | 放置位置与用途 |
| --- | --- |
| `toolName`、`owningPreset` | 根上的行身份字段，非 volatile；`owningPreset` 仅由两份预设补丁声明归属，用途见 6.2。 |
| `agentOptions`、`agentPreset`、`allowedAgentPresets` | 根上的非 volatile 委托配置键，与原生工具行同名同形；提供 3.3 的路由默认及可选预设。写入拒绝与行身份字段采用同一保护。 |
| `settings` | 唯一可就地更新的子树，包含全部可编辑字段；字段清单与计数以 5.6 字段表为唯一来源。 |

volatile 表示该配置节点可在运行中就地更新，Ref 是宿主提供的活值引用。具体声明是：字段对象包进 `transform`，在 `settings` 子树上调用 `.volatile().default({})`，字段自身不再逐个声明 `.volatile()`。schemastery 禁止 volatile 嵌套；重复声明会在 resolve 解析期抛错，这一点已有进程内探针依据。

resolve 输出只在固定的 `settings` 路径生成一个 Ref。构建快照时，先解包这个 Ref，再读取各字段。行身份和委托配置键始终留在根上的非 volatile 路径，不能搬入 `settings`。

**行身份字段保护**。身份字段一旦进入 volatile 子树，RPC 就能改写行身份：设置网关把 volatile 节点之下的一切路径视为可就地编辑（`isVolatilePath` 对 volatile 子树内任意路径返回真），`settings/update` 携带 `toolName` 即通过写入检查并持久化，loader 随后按普通值变更重挂本行——宿主行变成工具行、工具进全局工具层，正是需求 3.2 禁止并由 [bundle 声明](<../cordis.patch.yml>) 从文件层锁死的形态。身份字段因此固定在根对象的非 volatile 路径：`mutate` 的逐路径预检与 `update`／`replace` 合并结果的逐字段校验都对身份字段抛出可读拒绝，拒绝发生在候选进入持久化之前，RPC 路径写不进身份字段。行身份只能经 profile／补丁文件层变更：那是普通（非 volatile）值变更，loader 的变更比较将其判为普通差异并走重挂，fiber 以新身份重新装配。该保护由设置网关的路径检查承担，不依赖回调形态，降级态与初始态同样生效。静态依据：dsh `0.2.1-rc.4` 的 `@deepseek-ai/dsh-settings` 中 `isVolatilePath`／`volatileForm`／`write`、`@deepseek-ai/dsh-config-editor` 中 `edit`（落盘前 resolve 完整下一值）、`@deepseek-ai/cordis-plugin-loader` 中 `equalExceptVolatile` 与 volatile 提交路径；静态核读之外，该放置形态的身份保护链经进程内探针装置验证——隔离替身插件加真实宿主设置链的装置：RPC 携带身份字段在写入路径检查处被拒（`Config field "toolName" is not volatile`，patch 文件不动、不触发重挂），文件层增删身份字段走普通重挂并以新身份重新装配——该装置按 dsh `0.2.1-rc.4` 重跑（待验证）；被引符号与拒绝文案锚（`is not volatile`）已按 dsh `0.2.1-rc.4` 安装树核实在场；真机表单按 8.2 配置页面行验证。

**委托行级键的写入拒绝**。`allowedAgentPresets` 是非空 preset-id 白名单（宿主同款：dsh `0.2.1-rc.4` 的 `@deepseek-ai/dsh-tool-subagent` 以 `z.array(z.string().min(1)).min(1)` 在行配置解析层拒绝空数组）：键缺席＝未配置（`agent_preset` 不暴露）；键在场且为空数组＝非法，给可读拒绝（至少一项）。「空数组＋默认预设并存」整体按空数组拒绝，包含校验（`agentPreset` ∈ 允许集合）只对合法白名单执行，不存在白名单折叠为未配置后单独接受默认预设的形态。拒绝为两层、判据同源（在场空数组＝非法）：

- **原料层**——cordis 每次 resolve（装载、重挂、volatile 就地提交）都先让原始候选（物化之前的用户原文）流经 `internal/config` waterfall 再做 schema 解析（`Fiber._resolveConfig` 是统一配置解析入口；loader 的 `_commitVolatile` 是 volatile 路径的第二入口）。本包候选（归属甄别先行，外来候选直接续链）带该键且为空数组时在 waterfall 抛词典文案（`error.config.allowedPresetsEmpty`，两语成对；抛错通道无语言上下文，线上形态取英文档，与自检诊断原文按数据不翻译的通道纪律一致）中断本次 resolve：装载／重挂 fiber 置 inactive、行不激活；volatile 提交 loader 捕获记 warn、refs 不动、不重装载。
- **schema 层**——声明为原生同形 `z.array(z.string().min(1)).min(1).default(void 0)`。`.default(void 0)` 用于保留缺席语义：缺席键解析为 undefined，不携带自有键；若省略该默认声明，缺席键会物化成 `[]`，随后被 `.min(1)` 拒绝，导致未配置该键的行装配解析失败、行不激活。显式空数组与空串元素在 schema 层即抛错。装载、重挂、volatile 就地提交均执行 schema 校验；config-editor 落盘前的 resolve 与客户端草稿校验虽不经过 fiber 的统一配置解析入口，也由 schema 层执行同一空数组拒绝判据。`resolveConfig` 只搬运缺席（undefined）或非空名单两种合法解析结果。

RPC 写不进该键（非 volatile 路径保护，同上行身份字段）。既有两条委托键校验（非重复、默认预设包含）仍在 `resolveConfig`，装载 resolve 抛错置 inactive，与空数组拒绝同一出口（原料层先到一步给可读文案）。委托键不进 volatile 快照（配置视图按装载期值现取，6.2）。`agentOptions` 的无键物化折回未配置维持不变（原生对空对象无最少键数要求）；行身份字段及其保护不涉。

#### 5.1.1 写入前校验什么

`settings/update`、`replace`、`mutate` 都进入 `configEditor.edit`。它在 `writeFileAtomic` 前使用行 runtime 的 Config resolve 完整下一值，`settings` 的 transform 回调据此决定接受或拒绝。

校验组包含布尔 `silentFailureGuard`、`gitBashShell`、`askTakeover`、`workflowProgressLog`、`fullCommandEcho` 的类型，以及五条不等式：

- `minYieldMs ≤ defaultYieldMs`；`defaultYieldMs ≤ maxYieldMs`。
- `minWaitMs ≤ defaultWaitMs`；`defaultWaitMs ≤ maxWaitMs`。
- `pollIntervalMs ≤ maxWaitMs`。

布尔 schema 保留原候选值，交给回调检查，不把非法类型静默换成默认值。非法新写入在持久化前拒绝，用户覆盖、持久文件、refs 和有效快照都不被该写入改变。原因经 `settings/rejected` 原文返回，例如 `[async-tools] cross-field violation: defaultWaitMs=1 outside [minWaitMs=250, maxWaitMs=600000]`，保留两侧字段和值。降级快照仍以 `=== true` 归一布尔值，作为最后防线。

#### 5.1.2 按当前状态判断输入

回调有三态。**初始态**用于装配自检完成前，先允许解析；**武装态**表示正常校验已启用，对所有输入执行上述校验；**降级态**携带已解析基线，只对深度相等的原值放行，其余输入照常校验。这里「武装」是回调状态，不是 2.1 定时器的 arm 动作。

维护者先按下表决定操作，不要把「改了一个合法字段」误当作「完整下一值合法」：

| 输入条件 | 动作／判定 | 结果与修复出口 |
| --- | --- | --- |
| 装配自检未完成 | 初始回调允许解析，随后 apply 必须自检 | 合法转武装；非法捕获已解析基线并降级。初始窗口不是 RPC 写入口 |
| 正常校验已启用 | 检查完整下一值的五不等式及布尔类型 | 非法落盘前拒绝，原持久值、refs、有效快照不变 |
| 降级中，输入与基线深度相等 | 允许同值解析或重存 | 成功应答但仍降级，保留回退快照与警示；不是修复成功。启动回退为合法默认，运行中回退为上一合法快照 |
| 降级中，与基线不同且仍非法 | 拒绝，包括只改其他合法字段却保留原错误 | 返回 `settings/rejected`；先修非法字段，不能靠改别的字段绕过 |
| 降级中，完整下一值合法 | 保存，监听提交并重建快照 | 清基线、登记和警示，恢复武装态 |
| 文件手改非法 raw 被拒后要改普通字段 | 先从文件层把 raw 恢复合法 | 解除 `fiber.update` 解析阻断后才能重挂；常规不可达的等值刷新另见 5.1.5 |

首播以及每次合法 volatile 提交后都执行 apply 自检，通过即使用武装回调。自检失败（首播或刷新）进入降级，把活配置 `settings` Ref 解包所得的当次已解析值作为基线。已经降级时再次刷新失败，维持原基线，不重新取值覆盖。

#### 5.1.3 为什么保留同值解析

基线只允许那份未变化持久值继续解析。回调只看到已解析值，无法区分 loader 重解析和用户原样重存；因此两者深度相等都允许。原非法值已经在盘上，重存不改变状态，设置卡片仍显示原值并保留警示。武装态拒绝所有非法值；降级态唯一可放行的非法值就是基线本身。

宿主在多个位置 resolve，同值放行用于保住修复入口：

- 装配在激活前由 `Fiber._reload` 解析；抛错使 fiber inactive。`describe` 只收激活行，行未激活就没有设置卡片。
- `configEditor.edit` 在落盘前解析完整下一值。
- `_commitVolatile` 在改 refs 前解析；失败保旧 refs，不派发 `loader/volatile-update`。
- 普通值变更经 `Fiber.update` 时，进入活跃 update 先解析一次，重挂装配再经 `Fiber._reload` 解析一次。

这些时机按目标版静态核读。若始终对原非法值抛错，行和设置卡片会失去修复入口；保留基线不是放宽新输入。只改另一合法字段会使整体不同于基线，原错误仍在就必须拒绝。正确动作是把完整下一值修合法再保存。

#### 5.1.4 基线载体、序列化与投影

schema 解析确定：同一 raw 得到同一已解析值。因此比较已解析基线时，loader 把 simplify 最小形状写回 `options.config`（剥掉等于默认的键）不会制造假差异。部分 raw 补默认后仍按同一跨字段规则校验，非法重载保上一合法值的语义不变。

回调必须自包含，不能引用闭包或模块状态。schemastery 以 `toString` 序列化，再经 `new Function` 复活；表单重建、describe 输出有两跳，复活函数自身没有 `toJSON`。为避免第二跳丢 callback，回调的 `toJSON` 拼接内层函数和自身源码，产生自重建表达式，支持多跳及服务端／客户端 schemastery 副本。基线作为 JSON 字面量嵌入同一源码随之传递。

活 schema 回调对象是基线唯一载体；宿主行与工具行共用模块实例时保持一致。预设工具行只写身份，不携带 `settings` 覆盖，解析得到合法默认，即使不同于基线也能通过。客户端复活副本带同一基线，对相等草稿也放行，其余非法草稿两侧同拒；不另设客户端严格档。

`settings` 投影合同不变：schema 表单保留 transform 子树、5.6 字段表的全部字段键、无 volatile 残留；值投影在 `settings` 键下展平同一字段集。客户端重建后，合法通过、非法可读拒绝。进程内隔离替身加真实设置链装置已验证嵌套投影、武装态跨字段拒绝且 patch 不动、平铺写入被拒、合法单字段、`mutate` 增删及完整 `replace`；真机表单仍按 8.2 验证。volatile 嵌套禁令和自续序列化也有进程内装置依据。

#### 5.1.5 修复、文件手改和防御路径

**常规修复。** 合法 volatile 提交后，监听重建快照成功，换回无基线的武装回调，清降级登记及警示。`internal/config` waterfall 登记的「最近提交原始值自检失败」也在下次合法提交时清除。身份字段保护不依赖三态，始终生效。无降级启动不写基线；初始窗口不可经 RPC 写入，因为 `edit` 要求行已经存在且激活。

**文件手改非法 raw。** 它仍在 `_commitVolatile` 的 resolve 被拒：loader 保留 raw、旧 refs，不派发事件，waterfall 登记降级。留下的非法 raw 又会使后续普通值变更在 `fiber.update` 解析时失败，不能重挂，行继续用旧 refs。先在文件层把非法值改合法，才能解除阻断。相比之下，降级期间不同于基线的非法 RPC 输入在 edit 落盘前就拒绝，根本到不了文件。

**常规不可达的防御路径。** 武装态下，refs 更新表示回调已经放行，而复检使用同一判据，正常应同样成功；刷新失败只防御两处判据意外漂移。另一个「等值文件重写先刷新 refs、随后刷新失败保旧」的路径也只作防御说明：宿主 `_commitVolatile` 对与现值深度相等的候选不刷新 refs、不发事件（loader 静态核读），因此正常不能满足该前提，不设常规反例。

#### 5.1.6 发布快照与告警

loader 给 apply 第二参的 `settings` Ref，要在输入和 schema 输出两侧解包，再做同源逐字段／跨字段校验。宿主角色把合法值存模块级快照，订阅自己的 `loader/volatile-update` 重建，经 refresh-bus 通知工具。工具每次执行读当前快照；快照缺席时用合法本行备用值并通告。

两种降级来源必须分别说明：

- 启动损坏布尔或跨字段持久值：行与卡片保留，describe 显示原非法值，运行用合法出厂默认（两开关默认关），登记明细。
- 运行中刷新失败或非法重载被拒：保留上一合法快照，登记明细。非法重载挡在 refs 之外，raw 仍可能非法。

告警同时进入 stderr 和五工具描述尾部，含违例明细及修复指引，随 `agentLang` 提供 en／zh。共用模板须并列解释启动默认和运行中上一合法值，不能把两者写成同一来源。合法提交后撤警示，宿主行卸载清登记；登记、撤销及失败方向都经 refresh-bus 刷新描述。总线要求宿主与工具共用配置模块实例。真实保存到描述和行为的关系仍需接线与运行验证，不能从模块存在推断。

### 5.2 描述与两语

**修改位置与同步对象**。[描述构建](<../lib/descriptions.js>)从[两语表](<../lib/text.js>)取得五工具文案，从生效配置取得数值，整段构造描述及参数说明。工具定义会固化描述与参数 schema；刷新时就地更新宿主借用的定义对象，不注销再注册。

只有 `async_agent` 的 `agent_preset` 是动态条件参数。`provider`、`model`、`reasoning_effort` 恒声明；其余工具不增删构造时的条件键，例如 `async_run` 的提权两键仍按构造时条件声明。维护后端或预设选择时，按 3.3 的可选预设集合和当前后端能力重算 `agent_preset` 是否在场。刷新与 execute 入口共用同一函数，保证模型侧 schema、执行校验、描述和实际请求四处采用同一条件集合。

**触发输入与刷新结果**：

| 触发入口 | 要读取的输入 | 同步结果 |
| --- | --- | --- |
| 设置快照刷新 | 当前生效数值、语言、行配置及后端能力 | 更新描述、参数说明，按重算结果原地增删 `agent_preset`。 |
| 每次 execute 入口 | 当前后端与行配置，不沿用上次条件集合 | 现算支持键，校验未知键并构造实际请求，同时同步借用 schema 的条件键。 |
| `subagent/provider-added`／`subagent/provider-removed` 事件 | 当前后端注册状态；新增事件载荷携带后端现值 | 事件到达即重算模型侧 schema、条件键说明及任务书两语形态，无须先改设置或创建一次。 |

后端替换没有单独事件：宿主注销旧后端、重注册新后端，各发一条对应事件。同一后端对象内部的能力或继承方式变化不通过原地改值广播，须重注册后端。按此事件协议，注册、替换、移除、`agentPreset` 支持增减和 `inheritsParentContext` 变化都走同一刷新入口。

**事件缺失时：执行与模型投影分开判断**。事件丢失或尚未送达，不代表可以继续使用旧参数集合：

- execute 仍在入口读取当前后端能力，按新集合校验和构造请求，不因旧集合拒绝合法参数，也不携带已不存在的键。
- 模型尚未发起调用时看到的投影可能仍是旧值；它要到后续后端事件、设置变化或 execute 重算后才更新。执行正确不能证明模型投影已及时刷新。

**上下文可见性与两语任务书**。`async_agent` 的描述及 `prompt` 参数说明在上述重算点读取 `inheritsParentContext`。继承上下文的后端应说明子代理可见父对话，不写「看不到本对话」；独立新子代理仍要求自包含任务书（需求 3.1）。后端变化时，两语形态与条件参数一起刷新。

**验证装置与失败判据**。8.2 的动态 schema 事件任务分别验证刷新算法与事件接线：手动调用刷新函数只证明重算算法；还须发布受控 Cordis 注册／移除事件，观察模型投影随之变化。另设事件缺失对照，分别断言 execute 现算正确、投影在下一触发点前可能滞后。四处条件不一致、把手动刷新当事件证据或把执行正确当投影已刷新，都不能判通过。

模型文本 en 无混入中文、zh 逐键译全、键集相同；标识符和用户数据保持原样。界面词典独立选择，宿主插件元数据依宿主语言。错误、状态、返回 note 同属模型文案，不能只翻描述。模型侧与设置页共用概念的用词以设计 5.6 的术语表为准，内容选择同时按该节的受众与信息价值判据核对。

### 5.3 浏览器入口与官方表单

宿主行使用可解析的平名包，客户端模块图来自宿主 loader entry，不来自预设子树。package 的 web client 声明与 exports 同时在场。

配置区挂 `plugins.bundle.config`，key 为包名 `dsh-async-tools`，处于插件页描述与组件行之间。bundle props 不提供 form，客户端按 entry id `async-tools-host` 从 configForms 自取控制器，订阅替换快照并以 whileServed 守卫登记。

客户端依赖为 locale、ui-settings、ui-plugin-manager、api-gateway、ui-layout、ui-sidebar、ui-workspace 七项；真实到达浏览器由注入表和 DOM 验证，不能只看后端服务。

### 5.4 草稿、提交与恢复

输入先进入草稿模型。清空输入表示取消该字段的覆盖，恢复默认也只暂存 unset；保存只提交改过的 set／unset，并携 revision 一次 mutate。保存应答为假时按失败处理，草稿保留。

单字段校验进 parse：全部数值字段带下界与上界（预算毫秒字段、延长时长字段与 `maxResultChars` 下界 1，`askTimeoutMs` 下界 10000，上界按字段界表），非有限、非正或越界的草稿 parse 为非法。`maxResultChars` 是正整数（字符数的整数语义与三倍换算依据见 3.1，范围见需求 5.2），非整数草稿同样 parse 为非法。官方 `SettingsFormModel` 对 parse 非法只置布尔 invalid 并禁用保存，原因文本由字段壳层分档显示：越上界、低于下界、非整数、链式违例、非数字各档给键（非整数档用于 `maxResultChars`），链式键按不等式左值字段扩展。配置服务同样核验整数与区间，不能仅页面挡住坏值。毫秒与时长字段在有限区间内的小数按需求允许，不自加整数限制。

跨字段按五条不等式校验：`minYieldMs ≤ defaultYieldMs`、`defaultYieldMs ≤ maxYieldMs`、`minWaitMs ≤ defaultWaitMs`、`defaultWaitMs ≤ maxWaitMs`、`pollIntervalMs ≤ maxWaitMs`。每条不等式的比较值取「草稿优先、无草稿用生效值」，覆盖草稿与生效值的组合；违例叠加进表单 invalid，原因显示在不等式左值字段，文案指明参照字段。空或非法草稿不参与比较，只按单字段档处理。

统一字段壳保留只读提示、label-for、aria-describedby、aria-invalid；与目标官方控件的逐项形态对照仍待核（设计 5.3、5.5）。毫秒说明两段读数分别取生效快照与当前草稿，在说明行下换行呈现、带「生效」与「输入」两个标识：正数换算为秒文本，整数秒无小数、非整数最多两位小数；亚 10 ms 正值显示 `< 0.01 s`；空和非法值显示 `—` 占位，不出现误导数字。数值只用秒文本，存储单位仍是毫秒。输入件身份按 `plugin-config-<key>`，验收不依赖自绘 name 或任意类名。

设置页在表单顶部、全部字段之前呈现卸载风险提示块：默认预设指向本包预设时，停用或移除本包会让新建会话报 `agent-preset/not-found`，宿主不自动清除该选择；卸载前先在宿主设置切换到可用预设，已移除后按宿主设置入口清选或重选。提示为静态非交互文本，词典键 `uninstallRisk` 两语对应，深浅主题均可读。使用说明（中英首页及用户参考）保留同一指引的操作步骤，两处内容一致、详略分工：设置页给结论与动作，用户参考给完整步骤。提示内容自包含，不依赖卸载后即不在场的本包组件。

### 5.5 设置字段帮助：常驻说明与带圈问号

需求 5.5／5.6 要求每个设置字段提供常驻短说明与标签旁可点击的带圈问号帮助按钮，点击在字段下方展开详细解释、再点收起。机制如下。

**统一字段壳**。全部可编辑字段（5.6 字段表）共用一个自绘 `FieldShell` 组件（`EnumField`／`FlagField` 的合并扩展，值字段同用）。每字段渲染：

```text
div.ats-enum-field（字段列；上下 12 px，相邻字段 0.5 px border-l2 分隔）
  div.ats-enum-head
    div.ats-enum-labelGroup
      label.ats-enum-label（htmlFor = "plugin-config-<key>"；文本 = 需求 5.5 字段名称）
      button.ats-help-button（type="button"；带圈问号）
    span.ats-enum-badges（覆盖时：官方 Tag「已覆盖」＋「恢复默认」按钮）
  控件本体：值字段 input（numeric 字段加 inputMode="numeric"）、枚举 select、布尔官方 P.Switch
  p#<id>-invalid（非法时另加的非法原因行——位于说明行之前、独立 id、aria-invalid，红字呈现；常驻说明与毫秒读数保留，不因非法退场）
  p#<id>-message（常驻短说明＋毫秒读数——读数在说明下换行、带「生效／输入」标识，构成见设计 5.4；非法时另加非法原因行，口径见设计 5.4）
  div#<id>-help（role="region"；仅展开时渲染）
```

**当前方案与官方控件对照。** 当前设计选择自绘字段壳来满足需求 5.6 的带圈问号、常驻说明和字段下展开帮助。需求 5.4 允许在宿主未提供所需形态时复用字段外壳；目标 rc4 的 `SettingsValueField` 是否已满足要求、能否通过 `help` prop 或标签扩展复用，仍按 5.3 待核。不能用尚未核实的「固定 i 图标」或「无自定义按钮开口」排除它。先验证当前方案满足需求，再依据官方对照结果决定是否复用。

方案继续使用 `SettingsForm`、`SettingsFormModel`、`settingsNumberField`／`settingsTextField`、`P.Switch`、`P.Tag`、`P.IconQuestionOutlineRegular`。它们的名称在建资产中找到，但目标页面解析和实际导出绑定仍按 5.3 验证，不能在这里提升为运行有效结论。

**字段壳与输入件的设计尺寸。** 字段列上下 12 px，相邻分隔 0.5 px；标签字号 13 px、字重 500；输入件高 34 px、字号 13 px、圆角 12 px、边框 0.5 px；说明行字号 12 px；帮助区字号 12 px、行高 1.6。焦点描边取 `--dsw-alias-state-business-primary`。这些是当前采用值，不是目标版 `fields.module.css` 已逐项一致的结论；官方尺寸和焦点样式对照仍待按 5.3 核实。

**帮助按钮样式**（常态可发现是硬性要求，需求 5.6）：

- 按钮 24×24、圆角 8 px，图标 `P.IconQuestionOutlineRegular`（size 14）。
- 常态设计：0.5 px `--dsw-alias-border-l4` 轮廓＋`--dsw-alias-label-secondary` 图标色，字段说明行使用 label-tertiary。要求问号无需悬停即可发现，并与说明文字区分；实际可见性仍须验证。官方 helpButton 的边框、图标色和常态反馈待核，不以未核样式断言官方控件达不到要求。
- hover 与 `aria-expanded='true'` 的设计选色为 `--dsw-alias-interactive-bg-hover`；图标取 `--dsw-alias-label-primary`。`:focus-visible` 外廓为 2 px `--dsw-alias-state-business-primary`，偏移 1 px，设计上与输入件焦点共用别名。
- 当前设计不采用 `bg-layer-*` 族作为帮助按钮反馈色。目标 rc4 的 `bg-layer-1`／`2`／`3` 与底色关系、官方 helpButton 的 `bg-layer-4` 引用及其定义均待核，不能据此断言某别名未定义、两主题无反馈，或当前选色已稳定。按 5.3 的待核项对照主题定义和官方引用，再实测深浅主题计算值与反馈效果；若当前选色不满足反馈要求，依据核对结果调整设计。
- 别名名称由 `tools/check-alias-tokens.mjs` 静态检查；名称通过不证明 CSS 有值，也不替代上述视觉验证。
- 不附可见「说明」文字：带轮廓的问号已足够醒目，若每个字段的标签都附文字，只会增加噪声；需求 5.6 允许由设计定夺。可访问名称承载字段名（见下）。
- 不用错误或危险色制造醒目（需求 5.6）。

**开合状态与渲染层级**。`helpOpen` 是 `FieldShell` 内的 `useState(false)`，点击翻转。官方内建帮助是否采用相同机制，按 5.3 对照，不作为当前实现已等同的依据。展开区是字段列最后一个子节点，普通文档流渲染：无浮层、无 z-index、无高度上限，长解释与示例把后续字段下推，内容完整可见、不被裁切或遮住；收起时该节点不渲染。

**无障碍**：

- 可访问名称来自词典模板 `help.a11yName`（zh「{field} 的说明」／en `Help for "{field}"`，`{field}` 替换为字段名称）——包含字段名称（需求 5.6）。
- `aria-expanded` 随开合；`aria-controls` 指向 `<id>-help`；展开区带 `role="region"` 与同名 `aria-label`。
- 控件 `aria-describedby` = 非法原因行 id（非法时，居首）加说明行 id（在场时）加展开时的帮助区 id，空格连接；与目标官方控件的形态对照仍待核。布尔开关沿用 `P.Switch` 的 `label` 属性作无障碍名的既有口径（可见标签长在壳上）。
- 键盘：原生 button，Tab 可达、Enter／Space 触发，焦点外廓可见；触屏目标 24×24；焦点与展开状态由外廓、背景与区域出现共同表达，不只靠颜色。

**「帮助开合无副作用」的状态隔离**（需求 5.6）。帮助开合状态只存于 `FieldShell` 的组件局部 state。草稿与覆盖在 `SettingsFormModel`（`staged`／`plan`），非法与保存判定在 `shell()`，配置值在控制器快照——帮助状态不写入其中任何一处：按钮 onClick 只调 `setHelpOpen`，不触碰 `actions.edit`／`resetField`／`save`，不调 `mutate`，也不触发提问或任务操作，按钮 `type="button"` 不提交表单。反向同理：草稿键入、保存、语言切换引起卡片重渲时，`FieldShell` 以相同组件类型与元素 key 复用，局部 state 保留——只读、非法草稿、保存中三态下帮助保持可读，字段错误、读数与风险提示不因开合消失；离开页面卸载时帮助状态随组件丢弃，不进任何持久层。

**缺键回退**。当前语言的 `help.<key>` 缺席、或取值等于键名本身（裸键名）时，该字段不渲染帮助按钮——宁可少一个按钮，不开出空区域。`hint.<key>` 同口径：缺席或裸键名时说明行（含毫秒读数）退场，不渲染空段。正常路径由键集判据守：两档键集相等之外，两侧文案对账测试（two-planes，test/two-planes.test.mjs，覆盖设置界面词典与模型文本两侧）包含键集在场断言——5.6 字段表全部字段的字段名键、`hint.<key>` 与 `help.<key>` 两档全必须在场，删任一键即红；回退路径用删键反例测试。

**只读与保存中**。控件随 `!state.shell.writable` 禁用，帮助按钮从不设 `disabled`；说明行、读数与展开区照常渲染（需求 5.6 三态可读）。

### 5.6 文案：内容判定、分层、键位与统一术语

字段名称与功能语义按需求 5.5，常驻说明与展开帮助按需求 5.6。本节按需求 5.7 定义内容选择和验证方法，覆盖插件与预设简介、全部用户与 Agent 文案、公开使用说明及其中英文版本，不限于设置页。

**内容判定与分层**。先确认文案的受众和显示／返回时机，再判断它支持哪项操作或结果判断。设置说明回答用途与修改后的结果；Agent 文案说明调用时机、参数、返回和下一步——`async_workflow` 的描述按需求 2.4 必须同时说明使用条件与可用替代入口（3.4），这是 Agent 文案的判据之一。保留限制或警示时，须能指出省略后会发生的实际误设、误操作、误读或具体损失。无使用价值的内容直接删除，不以换成肯定句或移入帮助代替处理。

常驻说明提供用途、修改结果及操作前必须知道的条件；展开帮助提供有助于配置的关系、步骤和示例。必填、预算、审批、后台继续、未保存内容丢失、截断与找回、失败或结果未确认、卸载前动作等信息，按受众与实际触发位置就近保留。实现防护、校验反例和内部约束仍按各功能节执行，不据此要求设置说明重复完整规则；否定句是否保留由使用价值决定。

**词典键位**（[客户端](<../client.js>)的 `DICTIONARIES`，两档键集相同，`hint.*`／`help.*` 同受完整性检查）：

- 字段名称 `<key>`；常驻短说明 `hint.<key>`；枚举选项 `opt.<key>.<值>`。
- 展开区正文 `help.<key>`：段间 `\n\n`，渲染按段拆 `<p>`；首段展示配置键及适用的枚举值，作为技术标识补充，字段名称本身不带键名后缀。
- 帮助按钮可访问名称模板 `help.a11yName`（`{field}` 占位）。
- 校验文案五档（`invalidNumber`／`invalidRange`／`invalidBelow`／`invalidInteger`／`invalidPair.<键>`；`invalidInteger` 用于 `maxResultChars` 的非整数草稿）；`invalidPair` 的 `{ref}` 替换为当前界面语言的参照字段名称（链式命中返回键，显示层经词典换名），使用首次等待／单次等待术语。
- 操作按钮与状态：`save`／`saving`／`saveFailed`／`reset` 等操作按钮键，`readOnly`／`unavailable`／`overridden` 等状态键，沿用现行键组；中文自然具体，英文表达相同含义。
- 枚举选项默认标记与需求 5.2 一致：`opt.agentLang.en` 的英文选项、`opt.askUiSeat.sidebar` 的侧边栏底栏徽标选项附当前界面语言的默认标记；当前选择由控件状态表达。

## 6. 审批、静默失败与诊断

### 6.1 单次审批接线

命令解析当前 sandboxPolicy，仅在约束执行器可用时暴露提权字段。调用开始校验字段对，再经公开 approveEscalation 取得一次许可；许可返回后、注册与启动前复查取消信号，已取消时不注册、不启动并说明取消原因。随后 shell.resolve／starter 执行。

校验失败、非严格加宽、服务缺失、拒绝、取消均在进程启动前；无 executor 不给不可实现的指引。返回后的会话策略不变。沙箱标记与退出／signal marker 同时覆盖直接和后台输出路径。

### 6.2 防护签名与作用域

开关控制结果、描述与纪律三处，全部局限本包两个预设，三处判定时机不同。防护内容的归属判定统一按会话实际预设身份执行：运行时经 `sessions.get(主体 id)`（调用方 agent id；作业后台结算路径传 owner id，同一 id 空间）与 `sessionProjections.stateOf(session, 'agentPreset')` 读调用主体的实际预设（与 4.1 接管判定的实际预设读取——`sessions.get` 加 `sessionProjections.stateOf`——同一条同步读取路径，任一跳缺席或抛错按「不是本包预设」处理），工具行在场时再与该行归属声明值比对——会话预设不是本包两预设之一、与行声明值不一致或读取失败，一律不产生防护内容（失效安全方向＝防护关，需求 1.2、3.2、6.3）。结果诊断在执行期按此判定；自建预设的会话即使行上复制了归属声明，会话预设与声明值不一致，同样不产生。

描述警示是装载期静态文本：宿主工具投影按 agent 链分层解析可见工具，描述只取行上注册的静态串（经公开投影接口 `get(name, scope)` 与 `schemas(scope)` 读取），不存在按会话求值描述的机制。描述警示因此按工具行的装载组合判定：本包两份预设补丁的工具行在行配置中携带预设归属声明 `owningPreset`（值为本包预设名；行身份字段，性质同 `toolName`——非 volatile、无默认值，仅两份预设补丁文件设置，不是设置字段、不进设置表单）。归属声明只是候选条件，不构成充分条件，也不构成选用入口：警示段拼接还要求本行已核得「会话实际预设与声明值一致」的运行时证据——证据取自执行入口的归属判定（与结果诊断同一条读取路径），按行隔离记账：本行执行核得一致的证据只支撑本行的描述构建与刷新在场，未执行核得的其他行（含同声明值的复制行）不拼警示；核得不一致、尚未核得或读取失败时本行不拼（失效安全＝不产生；行装载后首次执行前无证据，警示段同样缺席）。自建行复制归属声明不生效：其会话预设与复制的声明值不一致，描述警示、结果诊断与执行纪律三处都不产生。声明是公开挂载入口的一部分，不禁用自定义挂载。

纪律 context 注册留在宿主行，组稿时按实际预设过滤：宿主 `systemPrompt.assemble` 把组稿上下文 `{agent, scope, signal}` 传给每个 context 的 text 函数，text 现读快照开关与目标 agent 的实际预设——经 `sessions.get(agent.id)` 与 `sessionProjections.stateOf(session, 'agentPreset')` 读取，与提问接管判定的预设路径同一条。预设不等于本包两预设之一时返回空串。宿主行是 bundle 声明的全局行、非预设提供、不携带归属声明，此处比对基准为本包两预设名单，等价于与两份补丁声明值集合的一致性判定。

组稿上下文无 agent、服务缺席、读取抛错或快照缺席一律返回空串；空段由宿主渲染层过滤，其他预设的组稿逐字不含本包内容。反向对照进入验证：开关开启时，其他预设新会话的完整组稿（sections、contexts 与工具表）与开关关闭时逐字一致。开关开启时，本包两预设的新会话包含纪律段，且随语言开关与快照现值更新。`silentFailureGuard` 只控制本节三处防护内容；常驻执行纪律段（3.5——异步等待纪律、委托规则与提问角色纪律的系统提示 section）不受该开关控制，本包两预设的组稿在开关关闭时同样携带，两段按各自判据分别过滤。

[诊断模块](<../lib/silent-failure.js>)签名：

- 捕获形：合并重定向、子表达式、变量赋值、输出重定向之一；不含普通管道。输出 trim 为空，实际受限、未提权、存在约束执行器且开关开，产生条件式提示；仅本次执行后端为 `pwsh` 时参与判定（3.1.1——捕获形启发式锚定本部署受限 PowerShell 的事实，Git Bash 后端下空输出不产生该提示）。
- 可见拒绝：英文 `failed to run` 与 `Access is denied` 同在，或中文 `无法运行` 与 `拒绝访问` 同在，产生附加说明，不改变权限判定或 status。中文签名没有对应实机语言环境时注明未验证。
- 两种签名因空白／文本条件互斥。它们仍有启发式误报范围，不把日志中命中锚对当成独立授权决定。

描述警告还要求提权字段已暴露。纪律段紧凑，模型语言现读；捕获形纪律的处置判据锚在「预期的输出缺失」上，与签名 1 的条件式口径一致——空输出本身不构成「未运行」结论（本就无输出的捕获形命令不触发该处置），裸调用重试与 `sandbox_permissions` 出路保留；部署特有杀软纪律仅在部署事实成立时使用，不加入通用结果签名。文本不能含未注册模板占位，以免组稿抛错。

### 6.3 异常与信息出口

只 reject 的 Promise 在创建点已有处理，所有可能同步抛的接线进入 finally 清理；query promise 迟到拒绝、动态 import 失败和 timer 回调错误不能逃逸到进程级异常。

模型可控日志值做 CR／LF／TAB 转义；模型侧宿主原错单行化并裁到 500 字符，完整线索保操作者日志。生命周期诊断通过 notice 出 stderr，不能写启动 stdout。环境集合仅取宿主 collect，溢出文件路径只报告实际值。

## 7. 包生命周期与兼容

### 7.1 装载和退役

本包进入 profile 的 dependencies 与 bundles 后，官方 loader 应用宿主行和两预设声明，浏览器模块按 web client 投递。只进 bundles 不进 dependencies 的页面可见性须单独核验。

预设声明移除即退出新会话花名册，已绑定 Agent 持有 generation 引用；retired 且 users 为零才 dispose 组合树。不能把声明退役写成所有活动会话立即销毁。

jobs 注册越过生产者／控制器 fiber，owner ctx 处置或作业服务 teardown 才取消并等待结算。只卸载工具行不取消已启动工作；非合规 producer cancel 不结算会影响清理，不能宣称 OS 级无孤儿保证。

待核验对象：dsh `0.2.1-rc.4` 的 `@deepseek-ai/dsh-agent-preset-registry` 中 generation 退役与释放、`@deepseek-ai/dsh-jobs-local` 中 owner 释放与服务 teardown，以及 `@deepseek-ai/dsh-subagent` 中 activation 所有权清理。三类生命周期分别验证，不沿用其他版本行号或验收结论。

### 7.2 默认选择与有限补救

注册表 selectedDefault 可能继续指向已撤预设，resolve 没有自动回退。卸载前提示用户选择可用预设；如选择仍失效，给明确清选／重选指引，而不是静默改用户默认。该风险在设置页提示块与使用说明两处醒目呈现（形态见 5.4），两处内容一致。

本包若提供独立检查或清理，必须不依赖已卸载运行模块，只处理识别为本包的声明和已知残留，保存用户原内容并拒绝不确定修改。卸载后的残留按本包边界处理：插件行卸载撤销保活链后，宿主完成通知按 2.3 照发，其文本由宿主生成、含指向原生读取工具的引导句，属宿主原文残留，按已知残留清点、不改写宿主文本。具体可预见问题先以隔离 profile 与真注册表验证；不要在真实在用实例试卸载。

安装件与开发树分离、发布来源可核对；开发链接（如 npm link）是明确的开发路径。重启仅从目标服务进程树外、确认无他人活动后进行，文档修改不要求重启。

### 7.3 版本和宿主依据

同一个插件包支持 dsh `0.2.1-rc.2`、`0.2.1-rc.3`、`0.2.1-rc.4`、`0.2.1-rc.5`（rc.5 已按第 9 章完成兼容验收，2026-10-31），统一在一条维护分支；目标插件版本为 `0.2.8+dsh.0.2.1-rc`（核心版本 `0.2.8`）。兼容基准与版本格式以需求 7.3 为权威；上述目标值不证明安装件可用、验收通过或已获发布授权。

**兼容线标识与支持集合。** `+dsh.0.2.1-rc` 是显示宿主兼容线的构建元数据，不是宿主版本范围，也不使插件核心成为预发布版本；机器准入由九个 `@deepseek-ai/dsh*` peer 的同一支持集合承担。[包清单](<../package.json>)的九个 peer 都声明 `0.2.1-rc.2 || 0.2.1-rc.3 || 0.2.1-rc.4 || 0.2.1-rc.5`，九条逐字符相同；缺一条或写成不同范围都不合格。正式 `0.2.1`、`0.2.0`、`0.2.2` 与未列入集合的新 rc 都不放行，即使语义排序更高或版本串相近。新增 rc 在同一维护分支完成兼容验证后扩充支持集合，不默认新建分支；rc.5 已完成兼容验收（第 9 章），CI 四档 Actions 实跑结果仍待推送后核对，不宣称 CI 已验证。

**准入只走 peer。** 宿主的兼容判定在 `engines.dsh` 在场时单独生效并忽略 peer，因此本包不声明 `engines.dsh`——它会把九条支持集合换成一条不经集合的判定。peer 的每条 range 由宿主语义版本判定（含预发布，`includePrerelease`），集合外的版本串不满足任一精确项，被拒载。版本豁免（allow-version 一类）、`engines.dsh` 覆盖 peer 或替换宿主源码都属绕过，不用于安装、装载或验收。

**支持集合按已验证的消费接口成立。** 四个宿主在本包消费的接口与服务契约上相同（rc.5 已按第 9 章的隔离真机验证补齐，rc.2–rc.4 按原验证记录），运行实现（`lib/`、`client.js`、`cordis.patch.yml` 与两份预设除头注）逐字节相同，因此同一实现可在四者上运行。加入集合的条件是已按第 8 章验证，不是版本串相近：新的 rc 须重新核对本包消费的接口与服务契约、通过多宿主准入矩阵与安装通路后才能写入集合。

**依赖来源与安装事实。** 九个 `@deepseek-ai/dsh*` peer 必须与当前宿主同一 rc，且实际解析来源为宿主安装树；`@deepseek-ai/cordis`、`@deepseek-ai/cordis-plugin-timer` 两个 peer 同样按宿主树解析，由宿主补齐——安装时 `autoInstallPeers:false`，不由本包带入，也不得来自 profile 本地副本或其他 rc 的重复包。dependencies 里的 `@deepseek-ai/schemastery` 与 `zod` 是直接叶子依赖：官方 CLI 的 runtime profile 映射（`routeScoped`）优先 profile 本地包，pnpm 可能把它们装成 profile 本地同版副本，这是官方安装的既定形态，不构成豁免；副本版本须与宿主同名包一致并满足各自范围，按实际解析记录来源，不因物理路径不同自动判为跨代或跨树。九 dsh peer 与两个配套 peer 的解析来源是强制判据，不因副本形态放宽。开发树与 CI 源码矩阵可全同树（junction 判据见 8.3）；真实安装按实际解析记录每个依赖的来源与版本（8.2）。配套范围为 `@deepseek-ai/cordis` `~4.0.5`、`@deepseek-ai/cordis-plugin-timer` `~1.1.7`、`@deepseek-ai/schemastery` `~3.18.5`、`zod` `~4.6.7`。

**发布标识与显示。** 发布标识从同一包版本取得插件核心与宿主兼容线，生成完整 Git 标签及宿主在前的 Release 标题；标题列出支持集合与插件核心版本（格式与目标值按需求 7.3.1），与管理页显示一致。管理页保留完整包版本 `0.2.8+dsh.0.2.1-rc`，不省略构建元数据；两语安装说明列出同一支持集合，不把兼容线写成支持所有 `0.2.1` 版本。构建元数据是兼容线标识，既不能与某个 peer 值作等值比较，也不能用常规 SemVer 相等或范围匹配证明九条 peer 与元数据一致——一致性按「元数据标识的线即支持集合的共同版本线，集合以 peer 原文为准」核对。标签与 Release 标题中的插件核心版本须与包版本一致。插件核心版本按自身发布递增；支持集合变化需重新交付时递增核心 patch，不只改构建元数据。

**服务契约与升级。** dsh peers 覆盖 import 和服务契约（清单见需求 7.3）；叶子 schema 库放 dependencies。代码依赖集合必须包含声明，解析到宿主同一代实现。升级核对工具、作业／命令、子代理状态与投递、模型策略 schema/fold、编排引擎、配置与客户端挂点，再用行为回归；升级验收同时核对同 profile 其他插件的状态，不把本包通过推广为整个 profile 通过。改支持集合须同时改包清单、版本与 peer 断言、junction 期望表（8.3）、CI 版本断言与安装说明，以及预设头注等元数据注释，不能只改一处让检查看似通过；不要只更改版本串使检查显示为通过。

**版本验证。** 版本验证使用隔离安装件：包管理器从完整标签取得包，宿主读取及装载含构建元数据的清单，管理页读回完整包版本。发布验证把包清单版本、完整 Git 标签、Release 标题与管理页显示核对为同一发布的四方一致：标签与 Release 标题从同一包版本取得，标题中的支持集合与插件核心版本须与包版本及全部 dsh peer 声明一致。将缺少元数据、集合少列或多列、标签不对应包版本、标题与包版本不一致及界面省略元数据作为反例；对不支持的宿主（正式 `0.2.1`、`0.2.0`、`0.2.2`、未列入的新 rc）另测 peer 拒载，并确认拒载不来自 `engines.dsh`。已有发布标签保持不变；固定安装引用包含本版本的提交，不继续指向只声明单个 rc 的旧包；Release 发布状态单独核对，不因元数据中的预览后缀自动推断插件为预发布。

## 8. 验证设计

### 8.1 分层与真实性

需求第 8 章是结果合同。离线替身、真实 cordis 接线、真实宿主模块和真实实例分层验证，分别记录版本、对象及证据能证明的范围。磁盘实体 hash 相等不证明进程内已经加载同一模块；页面截图、接口返回也都不能替代完整行为。相同实现的对应提交上的证据可按受影响条件复用，安装件、依赖解析、页面建资产与版本显示按实际宿主分别核对。支持集合内的宿主分别记账：一个版本通过不等于集合通过；九个 peer 解析自两棵树的那次结果不归属任何单个宿主版本。

验证在独立会话和隔离样本中执行；不得改他人未提交内容或停止他人任务。变异在内存或包外副本运行，先确认脚本是否原地写产品文件。必要权限经正常审批，不能直接把测试会话升成全权限跳过授权。

消息／取消即时性按可观测信号至工具返回或取消收场不超过 5000 ms 的真实运行窗口核验，当次预算至少 60000 ms，以排除预算自然到期路径。受控单元测试确认信号处理后竞速及时收敛；准备阶段同样设置反例。先到消息的入口关系定性窗口受 3.2 固定响应上限（2000 ms）约束——合法大 `pollIntervalMs` 加慢／挂起目录的反例必须仍在 5000 ms 响应窗内交回。总预算另以时钟和 2.1 的数值口径（单元装置 300 ms 调度容差、挂起查询专项 200 ms）验证，不能用这个消息响应窗口替代严格总预算测试。

#### 8.2.1 子代理创建与路由核对

**8.2.1-A 启动请求与立返**

- 核对 `startActivation` 的 `provider`、`label`、`request`、`signal`、`delivery` 位置及形状，要求 `delivery:'parent'`。
- 启动接受后立即返回，零前台等待；创建工具不出现等待参数。

**8.2.1-B 公共参数与允许预设**

- 对照目标 dsh 原生工具的名称、类型、必填条件、缺省和校验：`description`／`prompt` 必填，`cwd` 可选，`provider`／`model` 成对，`reasoning_effort` 可单独指定，`agent_preset` 按允许集合与后端能力暴露。
- 自定义行的 `allowedAgentPresets` 显式空数组必须可读拒绝；空数组与默认预设并存也整体拒绝。覆盖 5.1 的原料层词典文案和原生同形 schema 两层。
- schema 反例：显式空数组、空串元素抛错；键缺席解析为 `undefined`，不携带自有键。
- 原料层反例：本包候选显式空数组抛词典文案；并存同拒；缺席、非空、外来候选继续处理。词典键中英两档都在场。
- 未知参数明确报错并列支持键。宿主 request 支持 `outputSchema` 等字段，不得扩大本工具公开参数。

**8.2.1-C 条件参数与后端事件**

- 后端注册、替换、移除及能力变化后，核对 schema、校验、描述、实际请求四处同步增删条件键。
- `inheritsParentContext` 变化后，两套任务书文案随重算刷新。
- 通过受控 Cordis 发布 `subagent/provider-added`／`provider-removed`，再读取模型侧投影确认变化。手调刷新函数只证明算法，不能代替事件触发证据。

**8.2.1-D 合并、支持预检与拒绝**

- 先给配置覆盖设置 `reasoningEffort`，再显式请求不同于配置／父基准的成对路由且省略 `reasoning_effort`。核对 `requestedAgentOptions` 在叠请求前删除该配置强度，且删除先于支持预检；再以路由未变、显式提供强度作对照。
- 分别记录删除后的合并选项、`resolveCallConfig` 临时参数、实际 `startActivation` 请求及宿主合并结果。换路由且省略强度时，预检不使用旧强度；不得以此代替最终继承断言。核对预检返回值没有回填请求。
- 后端不支持可续或路由参数时，在创建前拒绝。
- 预检拒绝保留真实原因，附 `target_tool="async_agent"` 的列举／搜索指引，零派生。

**8.2.1-E 查询与创建使用同一配置**

- 后端未注册、不声明 `agentOptions`、缺 `prepareContinuable`，或创建行配置默认预设但后端不能独立选预设时，查询报告限制且不生成适用示例。相同配置下「查询允许、创建拒绝」即失败。
- 用真实 Cordis 装置核对 `tools.get` 对象同一性：本包创建行可见时确认身份并取其配置；原生行注册为 `toolName:'async_agent'` 时为未确认且无示例。
- 创建行与查询行分挂、后端不同的组合，必须按创建行判定，不能取查询行配置。
- 示例只使用目标可见参数；不暴露路由参数的目标不能出现 `provider`／`model` 示例。

**8.2.1-F 实际请求与回执来源**

- 用真实 descriptor 与实际请求核对回执，必须含 `started`／`agent_id`。
- 逐值比对实际路由及来源：显式请求、工具行默认、后端默认、父继承、未读到具体值。行配置只提供一侧形成混合路由时，`provider`／`model` 分写来源。
- 以 `resolveChildAgentOptions` 合并结果和实际子请求为依据，不只比较提示串。配置默认与父继承并存时按实际携带值，推理强度也单独核对。

**8.2.1-G 查询反例**

- 允许名单派生条目也经过同一 `query`。未列供应商的供应商内搜索无匹配时，返回空页且没有本页示例。
- 原生身份必须同时有会话投影与调用方作用域 `tool:<名>` 非空组稿段；`systemPrompt` 缺席或组稿抛错时报告读取失败／未确认。
- 同名遮蔽时未确认且无适用示例；真正原生工具的身份、参数、策略三段证据齐备时保持 allowed。

#### 8.2.2 实时策略测试清单

**8.2.2-A 保存后生效的范围**

同一旧会话内新增、删除路由、关闭／重开 dsh 开关，后续 `async_agent` 按当前配置放行或拒绝。恢复会话、多层子代理也一致。纯默认／继承派生不受名单变化误伤，已运行子代理不换模型、不停止。

**8.2.2-B 读取与启动前复查失败**

分别注入 `current()` 抛错（启用空名单、非法或重复路由）及设置服务缺席，要求按真实原因拒绝显式选择，不放行或换模型。启动前第二次读取再分别注入读取抛错、开关关闭、名单撤销，按 3.3 三分诊断核对原因、查询／重试出路及零派生。名单未变但读取失败时，不能说配置变化或路由已撤销。

**8.2.2-C 原生策略反向对照**

本包不注册同键投影、不改原生工具策略。对照全局新名单变化，确认原生旧会话策略未被本包改写。

#### 8.2.3 目录搜索与分页测试清单

**8.2.3-A 查询方式与匹配**

- 覆盖供应商分页、供应商内模型分页、跨供应商及供应商内搜索。
- 去空白、忽略大小写、包含匹配、空白等同省略；同名条目不合并。
- 供应商 ID／显示名命中时模型整组随行；供应商内与跨供应商命中集合一致。未列供应商按准确 ID 同判。
- `provider`＋`model` 返回准确模型和强度详情；元数据缺席如实说明；只有 `model` 时提示需要 `provider`。

**8.2.3-B 页边界与版本变化**

`page_size` 默认 20，范围 1—100，非法值可读拒绝。同版本顺序稳定，翻页不重不漏。策略、目录、目标变化后令牌失效，要求重查，不拼接新旧版本。续查对象携带全部筛选与令牌，直接执行应翻完全部页。

**8.2.3-C 部分失败与未列条目**

- 部分供应商失败不记零模型，总数只含已取得项，并标不完整。失败供应商空页显示读取失败，不冒充确证空目录。
- 允许但未列目录的准确 ID 保持可查，并入浏览、搜索和允许计数。标明来源，不编造名称与元数据；仅在名单中的供应商同判。
- 未列供应商来源说明与本页条目同时显示，第二条及以后准确 ID 同样进入中英正文。

**8.2.3-D 授权与独立挂载**

目录可见不证明授权或远端可用。查询单独挂载仍能查目录，并明确创建入口未确认。

#### 8.2.4 目标判断与示例测试清单

**8.2.4-A 目标选择**

`target_tool` 使用当前会话可见工具名，含用户配置名。省略时仅一个可识别候选才采用，多候选或不可识别不默认通用可用。具名不可见或不可识别时报告「不允许选择」，目录照常返回，不生成适用示例。

**8.2.4-B 本包工具身份、策略、后端**

- 用登记簿与 `tools.get` 同一性确认身份。同名外来定义、`get` 缺席或抛错、跨模块实例导致登记缺席，都为未确认，不用查询行配置冒充创建行。
- 受控假 `ctx.tools` 必须提供 `get`，与 `schemas` 有相同可见性。行映射经入口 `apply` 或直接登记建立。
- 身份确认后读取当前 dsh 策略及创建行后端，逐项核对注册、`agentOptions`、可续支持、默认预设对应的独立预设能力。

**8.2.4-C 原生工具三段证据**

身份需会话 `subagentModelSelectionPolicy` 投影与作用域 `tool:<名>` 非空段双依据，参数按可见形状，策略按会话投影。任一不可证则未确认并指出缺失段。自定义名称同判，不凭名称或形状加投影默认确认。全局新增／撤销与旧会话策略的双向差异分别核对。

**8.2.4-D 结论、计数与条目**

适用性与完整性分开。未确认目标时不出现允许计数，只报目录已知数并标未确认；确认允许时计入未列路由。目标允许时逐条按名单标可选／不可选，名单外不宣传可创建、无示例；本页无可选项也无示例。准确详情按该具体路由判定。

投影不可读、目标不存在、无显式路由参数、后端不支持，分别报告未确认或已确认限制和原因，不猜测、不改原生工具。

**8.2.4-E 调用示例与组合边界**

示例只含目标接受字段，不混入搜索、分页或本包返回字段；不宣传为适用于 `async_workflow.agent()` 或其他工作流。反向核对五工具默认只挂本包两预设，自建组合由用户负责，不被本包自动改写。


### 8.3 现有检查入口的边界

[包清单](<../package.json>)定义单元、语法、预设、编码、文档、模型文本和公开范围等入口。[验证说明](<../verify/README.md>)列安全前提和每个现有脚本的覆盖；它是运行说明，不补足需求或设计正文。

公开文档职责与写作规则见[文档原则](<documentation-principles.md>)。现行检查范围包含中英文首页、中英文用户参考、原则、需求、设计、贡献和验证说明；CHANGELOG保留真实历史。事实修改同步两语及相关测试，结构/路径检查不代替读者任务审查。实际安装包须核必要文档与相对链接。

真机探针按现行宿主形状维护：登录与 RPC 统一走 [RPC 通道](<../verify/_rpc.mjs>)（token 换 cookie 即用、`redirect:'manual'`、不追 Location）；会话驱动需要升档时用既有升档助手。宿主模块树的树根核验保持单一来源：树消费者经配置加载器或宿主解析钩子的环境变量契约取根，解析钩子自身是契约定义处、不列入消费者名单。开发树 junction 核验按支持集合判定 dsh* 版本：接受集合内任一 rc，但要求本次全部 junction 指向同一棵宿主树，其中 dsh* junction 同 rc 版本，zod、cordis 等按各自预期版本；该判据针对开发树与 CI 源码矩阵，真实 profile 安装的 dependencies 叶子按实际解析记录来源（允许 profile 本地同版副本），peer 仍须解析自宿主树；判据不连接实例、不访问网络，可在离线形态下判定，环境缺席与接线错误分开记录。

**探针锚与证据路径的形状契约**。判据锚按文案归属分两类，各自单一来源：

- **词典锚**（插件渲染文：工具返回注记、等待提示、状态行等）统一登记在[共享锚模块](<../verify/message-markers.mjs>)，逐字取自 `lib/text.js` 现行词典、两语成对并注明出处键名；真机脚本从该模块取锚，不自存正则副本（口径：以词典成句为判据的锚；跨键共用片段、代码构造的调用句式与组合场景取值不属词典锚）。反漂移回归以词典两档渲染文本对每个锚断言命中——锚与词典任一侧漂移都红，单语锚（只在一种语言下成立）同样红。
- **宿主渲染锚**（宿主工具结果与通知：`job_list` 行、完成通知等）按宿主现行渲染格式书写并注明宿主出处——`job_list` 行为 `<id> [<kind>] <status> — <label>`，完成通知为 `background job <id> (<kind>: <label>) finished [status: …]`，两者都是宿主文本、不随本包语言开关本地化。作业编号按不透明字符串对待，锚不得假定数字编号形态；锚回归须同时以真实不透明编号形态与旧数字夹具形态为正例（编号格式假设回潮即红），并以缺类型标识的自述文本、异类型行与非目标状态为反例。
- 判据只认工具结果或通知注入侧的结构化来源（`tool/result` 与 `tool/call` 按 callId 配对、`user/message` 的 source 形态），模型复述与让出句柄文案不作为作业状态的回退证据。
- 探针证据产物路径一律经 `join(目录, 文件名)` 构造，目录变量与文件名不得直接模板拼接；脚本头注声明的证据落点必须与实际写出位置一致。用法行同样必须自洽：从声明的执行目录出发，hook 与脚本参数都按该目录可解析。

**设置探针形状契约**。命名空间为宿主行 `async-tools-host`，读写与收尾恢复均使用根上的 `settings` 子树，不做多端点试写：

- `settings/describe` 只投影 volatile 表单字段。本包宿主行的唯一 volatile 节点是 `settings`，所以命名空间条目的 `value` 为 `{ settings: { …全部字段… } }`，读生效值必须取 `ns.value.settings.*`，不能用平铺或多形状回退掩盖契约变化。
- `settings/update` 稀疏合并，`patch` 为 `{ settings: { …改动字段… } }`；`settings/replace` 先复位 volatile 字段再设置，`section` 为 `{ settings: { …完整字段… } }`。两者只允许 volatile 子树内路径，直接放在根上的设置字段会被拒绝。`replace` 不能当作稀疏更新使用。
- 形状转换集中在共享设置助手中：读取助手严格检查命名空间、`value.settings` 与所需字段后，向调用者返回字段对象及 revision；更新／替换助手分别把字段对象包装成 `patch.settings`／`section.settings`。调用者只处理字段对象，不重复包装或解包。现有 `readNs`／`patchNs` 及其调用者、独立设置行为探针、使用 `replace` 的端到端和队列探针须统一经这一入口完成读写与恢复，不自带包装或解包。命名空间缺席或形状不符须使探针失败，不返回空对象继续运行。
- 设置行为探针内置可失败的形状验证：先保存原状态；显式绕过助手发送平铺 patch 作负向对照，断言 `settings/rejected` 且生效值不变；再发送嵌套合法更新并逐字段读回，另核对嵌套完整 `replace` 的语义。拒绝缺失、错误类别不符或读回不符均判失败。收尾在 `finally` 中恢复原状态并再次读取核对，恢复失败单独报错，不能被主断言掩盖。保存与恢复须同时核对用户覆盖层（`user.settings`）和生效值：存在的覆盖按原值恢复，原先缺席的覆盖用 `settings/mutate` 的 `['settings', 字段名]` 路径 unset，避免把原生效值写成新的用户覆盖。恢复后两层均与原状态一致才算收尾成功。

这些是探针维护与验收判据，不表示全部相关脚本已经执行。宿主设置服务的投影、合并、复位与路径检查按 dsh `0.2.1-rc.4` 的 `@deepseek-ai/dsh-settings` 中 `volatileForm`／`projectForm`／`describe`／`update`／`replace`／`isVolatilePath` 静态核对，运行结果须按 8.1 分层记账。

探针脚本与静态字符串锚的文件名含历史轮次编号时，编号不构成当前产品权威。改模型描述、入口状态和加时字段时同步修测试；不能因为旧断言要求旧文案就降低新需求。测试数量不固定，要求有效覆盖，不把超时终止、加载失败或未运行误记为变异捕获。
