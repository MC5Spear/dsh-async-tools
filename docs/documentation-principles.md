# 公开文档原则

本文说明怎样撰写和检查项目文档，适用于所有公开说明和项目自有注释。
其他文档引用本文，不另写一套相同规则。
法律原文完整保留。历史记录按记录职责保留。

## 文档分别回答什么问题

| 文档 | 应回答的问题 |
| --- | --- |
| [中文首页](<../README.md>)和[英文首页](<../README.en.md>) | 这是做什么的？我能不能用？怎样安装和开始使用？设置、排障和停用说明在哪里？ |
| [中文用户参考](<user-reference.md>)和[英文用户参考](<user-reference.en.md>) | 每个工具和设置怎样使用？参数有什么要求？任务处于什么状态？失败、提问、模型选择和卸载问题怎样处理？ |
| 参与指南（源码文档） | 怎样准备环境、修改、测试和提交？审查和发布由谁负责？ |
| 产品需求（源码文档） | 已批准的目标和行为是什么？有哪些权限、参数和验收要求？哪些目标尚未实现或验证？ |
| 设计说明（源码文档） | 当前实现怎样工作？失败时怎样处理？哪些实现或验证差距会影响使用和维护？ |
| 验证说明（源码文档） | 怎样运行验证工具？需要什么条件？有哪些副作用？怎样清理？检查了什么，还没有检查什么？ |
| 更新日志（源码文档） | 每个版本改了什么？对使用者有什么影响？升级时需要做什么？ |
| 许可与现有第三方通知 | 可以怎样使用和分发？需要保留哪些版权和许可声明？ |
| 本文 | 怎样组织、撰写、同步和检查公开文档？ |

源码文档不一定随安装包分发。请从对应版本的源码中阅读下列文件：

```text
CONTRIBUTING.md       参与指南
docs/requirements.md 产品需求
docs/design.md       设计说明
verify/README.md     验证说明
CHANGELOG.md         更新日志
```

AI 署名用于说明制作信息。它不能代替版权声明，也不是兼容或验证结论。

## 写作原则

### 1. 公开说明必须直白易懂

- 用常用表达把事情讲清楚，不让读者猜术语、缩写或省略的逻辑。
- 一句话表达一个主要意思，一段解决一个问题。多个条件或例外分别说明。
- 必须使用技术术语时，就近解释。命令、字段、模型 ID 和路径保留准确写法。
- 按目标读者的知识组织说明。面向开发者可以保留专业细节，但不用长难句压缩信息。
- 不设机械的字数上限。把长句拆开、改成列表，或移到参考页，都不等于已经写清楚。

### 2. 按读者的任务组织内容

每一段都应帮助读者作出判断或完成操作。先确定读者要做什么，再决定内容放在哪里。

首页直接给出当前适用版本、安装来源和开始使用的方法。不要要求安装者先看维护记录，才能判断能不能用。
用户参考补齐完整用法，也要按问题分节、解释术语和写清步骤。
给开发者和审查者的工作要求，放在对应维护文档中。

### 3. 先讲正常操作，再讲故障处理

操作说明按实际顺序写清三件事：要做什么、怎样做、怎样确认结果。
一步有多个顺序动作时，分成编号步骤。

安装介绍先说明必要条件，再给安装方法和成功后的检查方法。
不要把正常安装、少见故障和内部实现挤在同一段。
故障说明按“出现什么现象、先检查什么、接着怎样处理”组织。

必要条件和风险必须放在相关操作之前。
不能为了首页简短，把影响安装决定或操作安全的信息藏进其他文档。

### 4. 简化表达，不改变事实

需求记录已批准的目标。代码、配置定义和包清单说明当前实现。
两者不一致时，查明差异，说明尚未实现的部分，不降低已批准的目标。
目标、实现、发布和验证结果分别说明。

- 保留准确的版本、命令、参数、默认值、范围和单位。
- 保留必填条件、例外、权限要求、生效时间和失败处理。
- 参数和设置表逐项对应技术标识，不能用其他位置出现的正确值掩盖错误表项。
- 写清跨字段关系，并区分配置允许的范围与单次请求实际采用的范围。
- 不把“建议”“可能”“计划”“通常”改成确定承诺。
- 同一个概念使用同一个术语，不为避免重复而轮换名称。

### 5. 风险说明给出下一步

在相关操作旁写清：什么时候会发生、会有什么后果、怎样确认、接着怎么办。
能给出解决方法就写方法；需要维护者协助就写清求助对象和需要提供的信息。

保留影响操作、结果理解和安全的限制。删除与读者当前任务无关的排除说明和反复自证。
不以免责声明代替处理方法，也不在每一处重复相同警告。

### 6. 当前说明与历史记录分开

需求和设计说明当前要求、工作方法，以及影响判断的实现或验证差距。
逐次测试读数、维护者机器路径、授权过程和修订流水不放进现行正文。

更新日志保留真实发布历史。版本、日期和发布事实不能因润色而改变。
不机械改写全部历史条目。确需澄清难句时，保留原有事实和发布结论。
新增条目直接说明变化、使用影响和必要的升级操作。

### 7. 维护说明应能独立执行

开发、审查和验证所需的规则、命令和前提应写在仓库中。
不依赖维护者机器上的私有技能、路径或未分发材料。
说明谁来操作、操作哪个对象，以及应看到什么结果。
缺少必要环境时，说明不能执行哪一项以及下一步怎样处理。

## 中英文和事实同步

- 修改用户使用事实时，同时检查两语首页和两语用户参考。
- 两语适用同一版本。参数、默认值、范围、风险和恢复方法保持一致。
- 英文是完整操作说明，不要求读者再读中文需求或设计来补齐用法。
- 两语使用自然表达，不逐字翻译，不堆叠同义的中英文词。
- 两份首页顶部互相链接，两份参考也互相链接。首页链接本语言的参考。
- 维护资料可以注明使用的语言，但不能成为英文用户完成操作的必要前提。

## 安装包和链接

两语首页、两语用户参考和本文必须随安装包分发。
检查实际打出的包，确认文件齐全、版本正确、包内相对链接可打开。
只检查源码中有文件，或包清单中写了文件名，不足以证明安装包正确。

未随包分发的维护资料，要么链接到对应固定版本的源码，要么明确说明怎样从源码中找到。
不要写成指向包内不存在文件的相对链接。
发布前核对安装来源、包版本和要求的宿主版本，不编造标签或可取得的安装件。

## 按读者任务检查

### 先检查是否读得懂

审查者按目标读者的知识阅读，不用自己掌握的实现细节补齐文档遗漏。

- 第一次阅读，能否说清这一节在讲什么？
- 能否照着完成操作，而不用自己拆句、猜词或重新排列步骤？
- 必要术语是否有解释？条件、风险和成功结果是否容易找到？
- 读完更新说明，能否判断变化是否影响自己，以及是否需要操作？

### 再检查任务能否完成

| 读者任务 | 检查内容 |
| --- | --- |
| 安装 | 能选择真实可用的来源，确认插件、DSH 和 Node 条件，安装后确认已加载。 |
| 使用工具和设置 | 能找到本线全部参数、设置、默认值和约束，知道怎样保存和恢复。 |
| 读取后台结果 | 能找回任务标识，正确读取结果，区分等待结束、工作停止、最终状态和答案送达。 |
| 创建子代理 | 能区分执行方式与模型选择，理解本线的模型权限和策略何时生效。提供模型查询时，能用查询结果继续操作。 |
| 处理提问 | 能完成选择或自定义回答，理解到期、延长、迟到清理和送达失败后的处理。 |
| 停用和卸载 | 能先更换默认预设，处理自己的活动任务，在插件移除后恢复新会话。 |
| 参与维护 | 能准备环境、修改、测试和提交。运行验证工具前，能判断权限、副作用、隔离和清理要求。 |

自动检查保护可以稳定判断的事实、结构和路径，并保留有效的失败用例。
不要逐字锁定长段说明，也不要用句长或关键词数量证明可读性。
检查通过后，仍要完整阅读改动正文和必要上下文，不能只看关键词命中的几行。

独立测试根据需求选择方法，不局限于已有用例。
未执行、跳过或条件不足的项目，明确写为未验证。
文档修订、静态检查和离线测试，不等于宿主运行或平台兼容已经验证。
